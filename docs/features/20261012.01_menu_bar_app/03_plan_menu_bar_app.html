Summary

Three workstreams, run side by side, landing as two PRs.

  • summary builds the helper's summary, its signed auth mode, and the read mark's round trip (plain Node, plus the page's post of a mark it already keeps). It lands first, on its own, as PR 1. Nothing on screen changes yet.
  • macapp builds the Swift app against a committed sample summary and proof vectors, so it does not wait for the helper.
  • install builds, installs, rebuilds and removes the app, and teaches the CLI to start a stopped helper.

macapp and install land together as PR 2, the change Ken sees.

Step 0: Orchestrator setup

Done by the orchestrator before any builder starts, and committed to the feature branch.

  • The wire, written once. Add to docs/CONTRACTS.md: the reply.seen event row and the reply_seen field (the architecture's "Read marks"), the routes' paths, the summary's every field and type (the architecture's "summary.read response" made exact), and the signed-request wire (the architecture's "The signed-request wire").
  • Fixtures. test/fixtures/menubar/summary.json (every section filled), summary_empty.json, summary_many.json (120 waiting documents, long titles, a bidirectional-override title). After Step 0 the summary workstream owns these files and every change to them.
  • Proof vectors. test/fixtures/menubar/proof_vectors.json: a secret, and for a GET with an empty body, a POST with a JSON body, and a signed 409 answer, every input and the expected signature in hex. Node, the fake helper, and the Swift self-test each assert them.
  • Manifest. Add src/service/summary.js, src/service/menubar.js, src/cli/commands/menubar.js to src/shared/manifest.js with planned: true, so lint passes before the files exist.
  • npm script. Add check:menubar (node scripts/check_menubar.js) to package.json, and add it to npm run gate. It skips with a line on systems other than macOS. No builder edits package.json.
  • Capture probe. Try one small screencapture region and record on the progress page whether it is blank. That decides whether V29 and V32 screenshots come from an agent or from Ken.
  • Starting counts. Record the counts V33 uses: helpers, menu bar app processes, fake_helper.js processes, launchctl list | grep lahe-test, and lahe-test* plists in ~/Library/LaunchAgents.

Every builder's contract

Every packet carries this block, near the top:

  • Never remove a file. No rm, no git clean, no deleting temp specs, screenshots, .bak files or test-results/. Put a rebuilt dist/lahe-layer.js back with git checkout -- dist/lahe-layer.js. List anything you would remove under "To delete at cleanup" in your progress file.
  • Never touch Ken's real login items. No command you run loads, stops, rewrites or removes lahe-helper or lahe-menubar, or anything in ~/.local/state/lahe. Tests use lahe-test-<pid> labels, a temp home, and a temp state folder.
  • Work in your own worktree on your own branch. Never commit dist/. Never edit package.json or src/shared/manifest.js; ask the orchestrator.
  • Run npm run gate:unit. Run one named browser spec only when your change is browser behavior. Never the whole browser suite.
  • Every process and launchd job a test starts is stopped in teardown. Report the V33 counts before and after your test runs.
  • Read first: your leaf, the brief requirements and architecture sections it names, docs/CONTRACTS.md (the summary and the wire), and CLAUDE.md.
  • Write progress/phase6_workstream_<name>.md: what you built, the tests, anything that differs from this plan, and screenshots for anything on screen. Screenshots there use fixture data only, never Ken's real documents.
  • Hit a limit or find the plan wrong: ask the orchestrator in one line. Do not document around it.
  • No em dashes anywhere.

Steps

Step 1: The summary (workstream summary, PR 1)

Architecture: "Data / State Changes" (the reply.seen event, summary.json, what counts as waiting on you, the summary.read response, the summary.open request), "Key Flows" (the first two), "Failure Modes", "Security & Privacy Notes".

Task 1.1: The read mark's round trip

Spec: Move the unread rule (needsToSeeReply, unseenReplyIds and what they lean on) from src/layer/tab_done.js into src/shared/record.js, with tab_done.js calling it there; the rail's behaviour does not change. Add the reply.seen event to the closed vocabulary in src/shared/protocol.js, exactly as docs/CONTRACTS.md spells it. The projection folds it onto the item as reply_seen only when the stamp names the item's current reply, and drops and reports anything else. The page posts it through the outbox the way item.closed is posted, once per stamp, at the moment the rail writes its local mark; and a reply_seen on a polled record that matches the current reply is adopted into the local marks. summary.js owns summary.json with seeded_at, written on the first summary.read, and a fresh file on loss. Files: src/shared/record.js, src/shared/protocol.js, src/service/projection.js, src/layer/tab_done.js (the rule's home and the post), src/layer/sync.js (the post and the adoption), docs/CONTRACTS.md (the event row and the field, written by Step 0; the builder corrects it if the code has to differ), tests. Acceptance: V1, V3 to V7. Don't touch: how the rail draws a card or its "1 new" tag, replay, anything else in src/layer/.

Task 1.2: The one-review summary

Spec: The catalog reader exposes one review's summary on its own, and the Library's fold rule so the summary can count a folded document once, and the summary gains two things: open questions after the cutoff, and per-page newest agent reply times. Comment text still never leaves the reader. Titles lose control and Unicode format characters and are capped. Files: src/service/catalog_reader.js, tests. Acceptance: V2, V8, and the Library's own tests still pass unchanged.

Task 1.3: The summary and its cache

Spec: summary.js builds the response from one-review summaries (cached per review on size, modified time and inode of events.jsonl, review.json, meta.json and the reviewed document, plus catalog.json once per request), folded with the Library's rule, plus the window holders and session liveness. Fields exactly as docs/CONTRACTS.md. Wire the summary in src/service/index.js. Files: src/service/summary.js, src/service/index.js, the menubar fixtures, tests. A test compares nested key paths and value types with test/fixtures/menubar/summary.json in both directions. Acceptance: V9 to V13, V17.

Task 1.4: The routes

Spec: A new auth mode, AUTH.CLI_PROOF, exactly as the wire in docs/CONTRACTS.md: signed requests, a 30-second window on an injected clock, a nonce cache, constant-time comparison, and signed answers (errors included). It passes test/fixtures/menubar/proof_vectors.json. summary.read (GET) and summary.open (POST, JSON) use it, refuse any Sec-Fetch-* header, sit behind the Host check, are never catalog routes, and summary.open also refuses an Origin header. summary.read takes the app's summary_version and answers a mismatch with 409 SUMMARY_VERSION. summary.open runs catalog Open with handoff: false. Files: src/shared/protocol.js, src/service/routes.js, src/service/auth.js, tests. Acceptance: V14 to V16, V19, V20, V34.

Step test: npm run gate:unit green, and V19's browser spec green alone. The orchestrator rebuilds dist/ once and opens PR 1.

Step 2: The Mac app (workstream macapp, PR 2)

Architecture: "summary.read response", "summary.open request", "Install, rebuild, and Quit", "Failure Modes", "Security & Privacy Notes". Brief: R1 to R14, R17, R18, UX Notes.

Task 2.1: The app

Spec: One Swift file, macos/menubar/LaheMenuBar.swift, using AppKit only, and an Info.plist with LSUIElement so it has no Dock icon. Arguments: --state-dir, passed by the login item; the port comes from service.json. It reads cli-secret and service.json from the state folder, connects to 127.0.0.1 at the port service.json names, signs every request with the AUTH.CLI_PROOF wire in docs/CONTRACTS.md (CryptoKit HMAC), drops any answer whose signature does not check, asks summary.read every 5 seconds and when the menu opens, and draws the icon and the menu in the brief's order. The icon is a template image drawn in code from the review layer's speech-bubble mark (src/service/tab_icon.js), with the count beside it. Four looks: nothing waiting, a count (to 99, then 99+), not running, can't tell. Files: macos/menubar/LaheMenuBar.swift, macos/menubar/Info.plist, macos/menubar/README.md (what it is, how it is built, that nothing here is required). Acceptance: V28, V29.

Task 2.2: Opening, Quit, Stop, Start

Spec: A click calls summary.open and opens the returned address only when it passes the allowlist (http, no user part, library.lahe.localhost or a site name plus .lahe.localhost, port absent or the pages port), rebuilt from its parsed parts; url: null opens the Library. Hide exits with status 0. Stop runs launchctl bootout on the helper's label; Start runs bootstrap then kickstart. Labels and plist paths are constants in the app, never read from a file; tests set their own through a compile-time -D flag. Start does not check the plist's contents (architecture, "Install, rebuild, and Quit"). Errors go to menubar.log in the state folder.

Debug modes, none of which need any macOS permission: --self-test (the allowlist, count formatting, proof_vectors.json, and --decode <file> for a captured summary; non-zero on a failure), --snapshot <dir> (each icon look drawn on a light and a dark background, as PNGs), --dump-menu (the built menu's titles, order, enabled state and tooltips as JSON), and a flag that posts the wake notification so V29 can test it. Files: the same. Acceptance: V30, V31.

Task 2.3: Build check and fake helper

Spec: test/fixtures/menubar/fake_helper.js serves the sample summaries on a temp port, signs its answers by the wire (and checks proof_vectors.json at start), and can answer 401, a signed 409, a timeout, an unsigned answer, or nothing, so every look and every change between looks can be shown. While building, compile the app with a throwaway local command; the committed build recipe is install's. Hand back the exact file list and compiler flags you used. Files: test/fixtures/menubar/fake_helper.js. Acceptance: V29 snapshot images and menu dumps on the progress page; the file list and flags in the hand-back.

Step test: the app builds, passes --self-test, and shows every V29 look and change against the fake helper.

Step 3: Installing and keeping it working (workstream install, PR 2)

Architecture: "install.json gains a menubar block", "Install, rebuild, and Quit", "Failure Modes", "Security & Privacy Notes". Brief: R14 to R20. The existing login item: docs/ongoing/STABLE_ADDRESSES.md and src/service/login_item.js.

Task 3.1: Build and the app's login item

Spec: src/service/menubar.js, macOS only, holds the one build recipe: find swiftc with xcrun, copy the fixed file list from the installed clone's macos/menubar/ into a fresh temp folder, hash it there, compile it there with /usr/bin/xcrun swiftc and pinned flags (-swift-version 5, the host architecture, a macOS 13 floor; argument arrays, never a shell), and rename the result into <state>/menubar/Lahe.app only on success, write ~/Library/LaunchAgents/lahe-menubar.plist (RunAtLoad; KeepAlive only on a crash; the app's arguments pinned as absolute values), record the menubar block in install.json with the source stamp. Every system call goes through the injectable runner login_item.js already uses, so tests run on every system, and the label and home are seams so tests use lahe-test-<pid> and a temp home. scripts/check_menubar.js calls the same build function and runs the app's --self-test; it skips elsewhere than macOS. The file list starts as LaheMenuBar.swift and Info.plist; the orchestrator reconciles it with macapp's hand-back. Files: src/service/menubar.js, scripts/check_menubar.js, tests. Acceptance: V21, V22 (logic), V25.

Task 3.2: Install, uninstall, show, rebuild

Spec: lahe install on a Mac asks once whether to add the icon; --menu-bar and --no-menu-bar answer without asking; an existing install plus --menu-bar adds only the icon. On Linux and Windows the flag prints that it is macOS only. lahe uninstall removes the icon. New lahe menubar show (kickstart the app's item) and lahe menubar rebuild. Files: src/cli/commands/install.js, src/cli/commands/menubar.js, src/cli/index.js, tests. Acceptance: V21, V22, V23, V25.

Task 3.3: Rebuild on change

Spec: menubar.tick(env): on macOS with the icon installed, compare the source stamp of the fixed file list in the clone named in install.json (never a worktree) with the recorded one and, when it changed, rebuild in a child process, swap the app in, and restart it only if launchctl print says it was running. Confirm in your hand-back that the always-on helper runs its 15-second timer; the orchestrator wires the call in src/service/index.js. A failed build keeps the old app, writes the error to menubar.log and records it in install.json, and is not retried until the stamp changes again. Files: src/service/menubar.js, tests. Acceptance: V24.

Task 3.4: Starting a stopped helper, and status

Spec: startThroughItem bootstraps the helper's plist and then kickstarts when kickstart reports the job is not loaded, after checking the plist's contents are what login_item.js would write for the recorded install. Labels and paths are constants. lahe status prints one line on the icon. Files: src/service/login_item.js, src/cli/commands/status.js, tests. Acceptance: V26, V27.

Step test: npm run gate:unit green with the runner mocked. The real build against macapp's source happens at Task 4.1.

Acceptance Criteria

Standard (every feature inherits these; keep them verbatim):

    • Clear visual hierarchy and information architecture. You know where to look, and the page's organization makes sense.
    • Consistency with the rest of the app. Buttons look like our other buttons, hover states follow the same convention, primary and secondary carry the same color meaning they carry elsewhere.
    • Honest feedback. Toasts and status messages report what actually happened. Never an optimistic "done" for something still in flight, or something that failed.
    • Micro-animations that mean something. Motion signals state or direction; it isn't decoration.
    • Copy in the brand voice (the project's brand or voice doc).
    • Existing components reused and the style guide followed. Nothing reads as a stock framework default.

Plan review: Menu bar app

Reviewer: review-plan (orchestration and test plan). Read: the plan and its three leaves, the brief, the architecture, CLAUDE.md, and the code named below.

Summary

The three-workstream shape is right. The PR split mostly works, with one exception: the plan as written breaks the day-one promise (RF3). The biggest risks sit where two builders implement one thing from prose. The signed proof is written three times, the build recipe twice, and the summary shape is held only by a hand-written fixture. The code also shows two ways the count goes wrong that no row would catch. A background tab clears answers on its first claim (RF1). The summary's cache misses a deleted document (RF2). Two tests would run against Ken's real login items, and one of them stops his live helper (RF5). The Mac screenshots need a stated fallback for when the machine refuses permission (RF11).

Six high, fourteen medium, three low.

RF1 (high): a background tab's first claim marks the page as seen

  • Kind / area / where: defect, test plan. Task 1.1, rows V3 and V19.
  • Problem: In src/layer/sync.js (claimRequest), quiet is attention !== FOCUSED && quietHeartbeatMs !== null, and quietHeartbeatMs starts as null on every page load. So the first claim of every page says quiet: false, whether or not the tab is focused. The page also reloads itself in the background when its file is rebuilt (the reload path near line 2501). The common flow is: an agent edits the document and replies, the background tab reloads, and its first claim says "focused". The answer is then marked seen without Ken ever looking at it. Task 1.1 says "nothing else in the layer changes", which rules out the fix. V3 takes quiet at face value. V19's background case only covers a tab that was already loaded before the reply.
  • Why it matters: This is the failure Ken named: the count clears for something he never saw (R6, R3).
  • Change to the plan: Let Task 1.1 add an explicit focused field to the claim body, computed as attentionOf(doc) === FOCUSED at send time. The seen store reads that field, not quiet. A claim without it (an old bundle) falls back to V4's rule. Correct the architecture's sentence about quiet first, since the architecture is binding. Add a V19 case that follows test/browser/quiet_tab_polling.spec.js: force the page unfocused with addInitScript before its first claim, land an agent reply, trigger a background reload, and assert that the count stays.

RF2 (high): the summary's cache cannot see a deleted document or a Library rename

  • Kind / area / where: defect, test plan. Task 1.3, row V17.
  • Problem: Task 1.3 caches each review on the stat of events.jsonl, review.json and meta.json. But the reader decides "missing" from the document on disk (placeRow in src/service/catalog_reader.js calls exists(info.docPath)), and renames live in the catalog store, not in the review folder. Deleting the document, or renaming a row in the Library, touches none of the three cached files.
  • Why it matters: A deleted document stays under "waiting on you" until something else touches that review. That breaks R5 and R7, and makes a count that never clears (R3). A rename keeps showing the old name.
  • Change to the plan: Have Task 1.3 recheck file existence and the catalog store's names on every request, or add their stats to the cache key. Add three V17 cases: delete the reviewed document with no other change, and the next summary drops it; rename in the Library, and the next summary shows the new name; rewrite events.jsonl with the same size inside the same millisecond, and the cache still rebuilds.

RF3 (high): splitting into two PRs breaks "day one shows no number"

  • Kind / area / where: defect, orchestration. PR slicing, rows V1 and V32.
  • Problem: The architecture writes seeded_at the first time the new helper runs. That happens when PR 1 lands, which is before Ken installs the icon from PR 2. Every question and answer between the two landings counts on install day. V32 walks a copy of Ken's state folder, and that copy will already hold PR 1's seen.json. So V32 either fails, or the walker resets the file and hides the problem.
  • Why it matters: It breaks R4 and the brief's first success line ("On the day it is installed, the icon shows no number").
  • Change to the plan: Seed on the first summary.read, not on helper start. Marks written before that are harmless. Update the architecture's seen.json section before the code. V1 asserts that seeding happens on the first summary request. V32 starts from a state folder where PR 1's helper has already been running, and the walkthrough states that.

RF4 (high): a rebuild brings a hidden icon back

  • Kind / area / where: defect, test plan. Task 3.3, rows V23 and V24.
  • Problem: Task 3.3 rebuilds and then "restarts the app". A kickstart starts the app even after a clean exit, so a hidden icon reappears. A git pull in Ken's main checkout, often run by an agent, triggers that rebuild.
  • Why it matters: R17 says nothing an agent runs brings the icon back. No row catches this.
  • Change to the plan: After a rebuild, restart the app only if it was running (check the job's state with launchctl print). Otherwise swap the bundle and leave it stopped. Add to V24: with the app hidden, a stamp change rebuilds the app and does not start it.

RF5 (high): the Mac checks run against Ken's real login items, and one stops his live helper

  • Kind / area / where: risk, orchestration. Task 4.1, the Step 3 step test, rows V31 and V32.
  • Problem: SR6 compiles the labels lahe-helper and lahe-menubar in as constants. Task 4.1 runs lahe install --menu-bar on a copy of Ken's state folder. That rewrites ~/Library/LaunchAgents/lahe-helper.plist to point at the copy, and loads it under Ken's real label. V31's "Stop unloads the helper" runs launchctl bootout gui/<uid>/lahe-helper from inside the app. That is Ken's live helper, which every running agent and open review depends on. The Step 3 step test ends with lahe uninstall, which removes the real items.
  • Why it matters: An agent's test run stops Ken's working tool partway through his day, and it may leave his login item pointing at a scratch folder.
  • Change to the plan: Add a test-only label seam. install.js already accepts d.label and d.home (the earlier spike's unique label). RF6 (high): the signed proof is implemented three times from prose, with no test vectors

  • Kind / area / where: risk, orchestration and test plan. Step 0, Tasks 1.4, 2.1 and 2.3, row V34.

  • Problem: The summary builder writes the scheme in Node, the macapp builder writes it in Swift, and the macapp builder's fake_helper.js writes it a third time, in parallel and from one paragraph. The prose leaves many choices open:

    • the exact string that is signed: route name or path, separators, and the timestamp's unit and format
    • how the nonce is encoded
    • the hash of an empty GET body
    • header names
    • how summary_version travels on a GET, and whether the signature covers it
    • whether the key is the secret file's raw bytes or decoded text, and how a trailing newline is handled
    • what the answer's signature covers

    The macapp builder's Swift and fake helper will agree with each other, because one person wrote both. The first time anyone checks them against the real helper is Task 4.1.

  • Why it matters: One mismatch means the app shows "can't tell" forever. It surfaces only at integration, after both builders have finished.

  • Change to the plan: In Step 0, write the exact wire into docs/CONTRACTS.md: route paths, headers, the canonical string, encodings and the version transport. Commit test/fixtures/menubar/proof_vectors.json with a secret, inputs, and the expected request and answer signatures in hex, including a GET with an empty body. Three checks assert those vectors: a Node unit test against auth.js, the fake helper's own start-up check, and the Swift --self-test. In Task 4.1, run the app once against the real helper on a temp state folder, not only against the fake one.

RF8 (medium): two builders write the app's build recipe
