Summary

Three workstreams, run side by side, landing as two PRs.

  • summary builds the helper's summary and the seen marks (plain Node, every system). It lands first, on its own, as PR 1. Nothing on screen changes yet.
  • macapp builds the Swift app against a fixed sample summary, so it does not wait for the helper.
  • install builds, installs, rebuilds and removes the app, and teaches the CLI to start a stopped helper.

macapp and install land together as PR 2, the change Ken sees.

Every builder's contract

Every packet carries this block, near the top:

  • Never remove a file. No rm, no git clean, no deleting temp specs, screenshots, .bak files or test-results/. Put a rebuilt dist/lahe-layer.js back with git checkout -- dist/lahe-layer.js. List anything you would remove under "To delete at cleanup" in your progress file.
  • Work in your own worktree on your own branch. Never commit dist/.
  • Run npm run gate:unit. Run one named browser spec only when your change is browser behavior. Never the whole browser suite.
  • Every process a test starts is stopped in teardown. Report the helper count before and after your test runs.
  • Read first: the brief's requirements named in your leaf, the architecture sections named in your leaf, CLAUDE.md, and docs/CONTRACTS.md where your leaf says so.
  • Write progress/phase6_workstream_<name>.md: what you built, the tests, anything that differs from this plan, and screenshots for anything on screen.
  • Hit a limit or find the plan wrong: ask the orchestrator in one line. Do not document around it.
  • No em dashes anywhere.

Steps

Step 1: The summary (workstream summary, PR 1)

Architecture: "Data / State Changes" (seen.json, what counts as waiting on you, the summary.read response, the summary.open request), "Key Flows" (the first two), "Failure Modes", "Security & Privacy Notes".

Task 1.1: Seen marks

Spec: seen_store.js owns seen.json: seeded_at on first run, per-review per-page marks in prototype-free objects, writes only when a write would change a count, a fresh file on loss. A page over 1024 characters, or one that is not a page of that review carrying an agent reply, marks nothing. reviews.js calls it on every claim and heartbeat that carries a valid review token and quiet: false, whether or not the window gets the rail. src/layer/sync.js adds the page's path as page to its claim and heartbeat bodies; nothing else in the layer changes. Files: src/service/seen_store.js, src/service/reviews.js (claim and heartbeat handlers only), src/layer/sync.js (claim body only), src/shared/protocol.js (the claim's request description), tests. Acceptance: V1, V3 to V7. Don't touch: the rail, replay, anything in src/layer/ but the claim body.

Task 1.2: The one-review summary

Spec: The catalog reader exposes one review's summary on its own, and the summary gains two things: open questions after the cutoff, and per-page newest agent reply times. Comment text still never leaves the reader. Titles lose control and Unicode format characters and are capped. Files: src/service/catalog_reader.js, tests. Acceptance: V2, V8, and the Library's own tests still pass unchanged.

Task 1.3: The summary and its cache

Spec: summary.js builds the response from one-review summaries (cached per review on the stat of events.jsonl, review.json and meta.json), the window holders, the seen marks, and session liveness. Caps and names as in the architecture. Files: src/service/summary.js, tests. Its output keys match test/fixtures/menubar/summary.json. Acceptance: V9 to V13, V17.

Task 1.4: The routes

Spec: A new auth mode, AUTH.CLI_PROOF: a signed request (timestamp, nonce, HMAC-SHA256 keyed by the CLI secret over route, timestamp, nonce and body hash), a 30-second window, a nonce cache, and a signed answer. summary.read (GET) and summary.open (POST, JSON) use it, refuse any Sec-Fetch-* header, sit behind the Host check, are never catalog routes, and summary.open also refuses an Origin header. summary.read takes the app's summary_version and answers a mismatch with 409 SUMMARY_VERSION. summary.open runs catalog Open with handoff: false. Files: src/shared/protocol.js, src/service/routes.js, src/service/auth.js, tests. Acceptance: V14 to V16, V19, V20, V34.

Step test: npm run gate:unit green, and V19's browser spec green alone. The orchestrator rebuilds dist/ once and opens PR 1.

Step 2: The Mac app (workstream macapp, PR 2)

Architecture: "summary.read response", "summary.open request", "Install, rebuild, and Quit", "Failure Modes", "Security & Privacy Notes". Brief: R1 to R14, R17, R18, UX Notes.

Task 2.1: The app

Spec: One Swift file, macos/menubar/LaheMenuBar.swift, using AppKit only, and an Info.plist with LSUIElement so it has no Dock icon. Arguments: --state-dir, passed by the login item; the port comes from service.json. It reads cli-secret and service.json from the state folder, connects to 127.0.0.1 at the port service.json names, signs every request with the AUTH.CLI_PROOF scheme (CryptoKit HMAC), drops any answer whose signature does not check, asks summary.read every 5 seconds and when the menu opens, and draws the icon and the menu in the brief's order. The icon is a template image drawn in code from the review layer's speech-bubble mark (src/service/tab_icon.js), with the count beside it. Four looks: nothing waiting, a count (to 99, then 99+), not running, can't tell. Files: macos/menubar/LaheMenuBar.swift, macos/menubar/Info.plist, macos/menubar/README.md (what it is, how it is built, that nothing here is required). Acceptance: V28, V29.

Task 2.2: Opening, Quit, Stop, Start

Spec: A click calls summary.open and opens the returned address only when it passes the allowlist (http, no user part, library.lahe.localhost or a site name plus .lahe.localhost, port absent or the pages port), rebuilt from its parsed parts; url: null opens the Library. Hide exits with status 0. Stop runs launchctl bootout on the helper's label; Start runs bootstrap then kickstart. Labels and plist paths are constants in the app, never read from a file. Errors go to menubar.log in the state folder. A --self-test flag runs the allowlist, label check and count formatting and exits non-zero on a failure. Files: the same. Acceptance: V30, V31.

Task 2.3: Build check and fake helper

Spec: scripts/check_menubar.js compiles the app with swiftc into a temp folder and runs --self-test; elsewhere than macOS it prints that it skipped. test/fixtures/menubar/fake_helper.js serves the sample summaries on a temp port and can answer 401, 409, a timeout, or nothing, so every look can be shown and screenshot. npm run check:menubar runs the build check. Files: scripts/check_menubar.js, test/fixtures/menubar/fake_helper.js. The orchestrator adds the npm script. Acceptance: V28, V29 screenshots on the progress page, light and dark.

Step test: npm run check:menubar green on a Mac; screenshots of each look against the fake helper.

Step 3: Installing and keeping it working (workstream install, PR 2)

Architecture: "install.json gains a menubar block", "Install, rebuild, and Quit", "Failure Modes", "Security & Privacy Notes". Brief: R14 to R20. The existing login item: docs/ongoing/STABLE_ADDRESSES.md and src/service/login_item.js.

Task 3.1: Build and the app's login item

Spec: src/service/menubar.js, macOS only: find swiftc with xcrun, copy the fixed file list from the installed clone's macos/menubar/ into a fresh temp folder, hash it there, compile it there with /usr/bin/xcrun swiftc (argument arrays, never a shell), and rename the result into <state>/menubar/Lahe.app only on success, write ~/Library/LaunchAgents/lahe-menubar.plist (RunAtLoad; KeepAlive only on a crash; the app's arguments pinned as absolute values), record the menubar block in install.json with the source stamp. Every system call goes through the injectable runner login_item.js already uses, so tests run on every system. Files: src/service/menubar.js, tests. Acceptance: V21, V22 (logic), V25.

Task 3.2: Install, uninstall, show, rebuild

Spec: lahe install on a Mac asks once whether to add the icon; --menu-bar and --no-menu-bar answer without asking; an existing install plus --menu-bar adds only the icon. On Linux and Windows the flag prints that it is macOS only. lahe uninstall removes the icon. New lahe menubar show (kickstart the app's item) and lahe menubar rebuild. Files: src/cli/commands/install.js, src/cli/commands/menubar.js, src/cli/index.js, tests. Acceptance: V21, V22, V23, V25.

Task 3.3: Rebuild on change

Spec: On macOS with the icon installed, the helper's existing 15-second timer compares the source stamp of the fixed file list in the clone named in install.json (never a worktree) with the recorded one and, when it changed, rebuilds in a child process and restarts the app. A failed build keeps the old app, writes the error to menubar.log and records it in install.json, and is not retried until the stamp changes again. Files: src/service/menubar.js, the timer's call site in the helper, tests. Acceptance: V24.

Task 3.4: Starting a stopped helper, and status

Spec: startThroughItem bootstraps the helper's plist and then kickstarts when kickstart reports the job is not loaded, after checking the plist's contents are what login_item.js would write for the recorded install. Labels and paths are constants. lahe status prints one line on the icon. Files: src/service/login_item.js, src/cli/commands/status.js, tests. Acceptance: V26, V27.

Step test: npm run gate:unit green; on a Mac, lahe install --menu-bar --state-dir <temp> against the macapp branch builds and starts the app, and lahe uninstall leaves nothing behind.

Acceptance Criteria

Standard (every feature inherits these; keep them verbatim):

    • Clear visual hierarchy and information architecture. You know where to look, and the page's organization makes sense.
    • Consistency with the rest of the app. Buttons look like our other buttons, hover states follow the same convention, primary and secondary carry the same color meaning they carry elsewhere.
    • Honest feedback. Toasts and status messages report what actually happened. Never an optimistic "done" for something still in flight, or something that failed.
    • Micro-animations that mean something. Motion signals state or direction; it isn't decoration.
    • Copy in the brand voice (the project's brand or voice doc).
    • Existing components reused and the style guide followed. Nothing reads as a stock framework default.
