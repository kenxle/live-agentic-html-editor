Summary

Section 1

The helper gains one read-only answer, the summary, plain Node in src/service/ that runs on every system. The rail's own read mark, the one behind a card's "1 new" tag, is posted to the review's store as an event, so the helper knows what Ken has read without a rule of its own. A Swift program in a new top-level macos/ folder draws the icon and menu from the summary. lahe install builds that program on the Mac with swiftc, puts it in the state folder as a small app, and starts it at login with its own login item. The helper rebuilds the app when its source changes. The app proves its permission with a signed request keyed by the CLI secret, so the secret itself never travels, and it trusts only answers the helper signs back. No agent-facing behavior changes.

Analysis of Existing Structure

Section 2
  • The catalog reader (src/service/catalog_reader.js) already builds, per review, the title, pages, address, last-worked time, waiting count, and its session's liveness. It is read-only and never returns comment text. Building the whole list takes about 150 ms warm and 870 ms cold on Ken's 690 reviews, measured with scripts/time_catalog.js on 2026-10-12. Too slow to rebuild every few seconds; fine to rebuild one review at a time.
  • The rail's read mark (src/layer/tab_done.js, src/layer/store.js): a card shows "1 new" until Ken opens it. The rule for which replies need reading (needsToSeeReply: a question, a refusal, or an answer the agent flagged with words behind it; never a tool round or a card he closed) and the mark itself (item id to record.replyStamp, the reply's time plus the revision it answered) live in the browser's storage only. The helper never hears about them.
  • Mark as done (item.closed) shows the shape to copy: an explicit event the page posts through its outbox, naming an item and a revision, that the projection folds onto the item in review.json and the merge rule treats as the store's.
  • Window holders (src/service/reviews.js): every review page claims and heartbeats every 10 seconds. The helper persists holders to windows.json. That is what "open documents" stands on.
  • Replies carry an at time once folded. The helper is the single reader of reply files and the single writer of events.jsonl, so every change to a review moves that file.
  • Agent sessions and monitor heartbeats (src/service/agent_sessions.js) already answer "is this session's agent listening".
  • The CLI secret (<state>/cli-secret, owner-only) and the AUTH.CLI_SECRET mode already exist for site.bind and review.retire. Those routes refuse any request with an Origin header.
  • The login item (src/service/login_item.js, src/cli/commands/install.js) writes ~/Library/LaunchAgents/lahe-helper.plist and records install.json. The CLI starts an installed helper with launchctl kickstart.
  • Catalog Open (src/service/catalog_actions.js) binds a document's site and returns its address.

What stays the same: every existing route, the Library page and its token, the agent contract, the review layer bundle.

Data / State Changes

Section 4

Read marks: the reply.seen event

The page already decides when a reply is read: the card is opened, and the rail drops its "1 new" tag. At that moment it also posts one event through its outbox, the same path Mark as done uses:

reply.seen, {item, stamp}, no record. stamp is record.replyStamp(item), the reply's time plus the revision it answered, at most 64 characters. The projection records it on the item as reply_seen only when it names the item's current reply; a stamp for an older reply is dropped and reported, like a stale reply. review.json does not carry it: agents read that file on every wake, and a read mark is not for them. The mark travels on records.read and on the reply poll, and the summary reads it by folding events.jsonl. Nothing else about the item moves: it is not a lifecycle transition, and the agent never sees it.

Both sides run one rule, moved from src/layer/tab_done.js into src/shared/record.js: a reply is unread when needsToSeeReply says it needs reading (a question, a refusal, or an answer the agent flagged and put words behind), it is not a tool round, the reviewer has not closed the card, and the recorded stamp is not the current reply's. The rail's "1 new" and the icon's count are that one function over the same records.

The page adopts marks too: a reply_seen on a polled record that matches the current reply is written into the browser's own marks. So a reply read in one browser stops saying "1 new" in another, which it does not today. A page from an older bundle posts nothing, so its count holds until the page reloads, and never clears early.

summary.json (state folder, helper-only writer)

{ "version": 1, "seeded_at": "2026-10-20T14:02:11.000Z" }. seeded_at is written on the first summary.read, which is the first time the installed app asks. Any agent reply older than it counts as read. Seeding on helper start would count everything between PR 1 landing and the install. A missing or unreadable file starts fresh with seeded_at = now, which can only make the count smaller.

One document reviewed by several reviews (one folded Library row) counts once: the summary folds with the Library's own rule after building each review.

What counts as waiting on you

A document waits on you when it holds an item the shared unread rule names (R5), whose reply arrived after seeded_at. There is no second rule: a question is unread until its card is opened, like any other reply the rail tags "1 new", and the rail's "question" tag on an opened card is the rail's business.

Neither counts for a retired review, a review with ended_at, or a document the reader marks missing (R7).

The icon counts documents, not cards: each one is one click. Today 45 documents have an old open question (64 questions; 34 from the last month), counted by scripts/count_questions.py on 2026-10-12. The seeded_at rule keeps all of them out.

  • Open, connected and recent lists are capped at 8 in items, with more for the rest (R12). Waiting on you is not capped. sessions.open counts sessions not closed. library_url is the Library's printed address, with the pages port when the port-80 forward is not proved.
  • The exact field list, types, and the signed-request wire below are written into docs/CONTRACTS.md before any builder starts, and a fixture and proof vectors are committed beside them (plan, Step 0).
  • No comment text, no tokens, no absolute paths, the same rules as the Library list. Titles have control characters removed.
  • A session is connected when agent_sessions liveness says its agent is listening (a live monitor) or working (a lahe command in the last few minutes), the same test the Library shows (R10).
  • An open document is a review whose window holder is current, focused or not.
  • A session's name is its Library rename if Ken gave one, else the title of its most recent review.

The signed-request wire (AUTH.CLI_PROOF)

  • Key: the text of <state>/cli-secret with surrounding whitespace removed (64 hex characters), used as its UTF-8 bytes.
  • Request headers: x-lahe-proof-ts (Unix time in milliseconds, decimal), x-lahe-proof-nonce (16 random bytes as 32 lowercase hex characters), x-lahe-proof (lowercase hex HMAC-SHA256).
  • What is signed: the lines lahe-proof-v1, the method, the path with its query string exactly as sent, the timestamp, the nonce, and the lowercase hex SHA-256 of the body (of the empty string for a GET), joined by \n with no trailing newline.
  • The version travels as ?v=1 on summary.read, so the signature covers it, and as summary_version in summary.open's JSON body.
  • The answer carries x-lahe-proof-reply: HMAC-SHA256 with the same key over the lines lahe-proof-reply-v1, the request's nonce, the status code, and the hex SHA-256 of the response body. Error answers are signed too, so the app can tell the helper's 409 from a squatter's.
  • The helper accepts a timestamp within 30 seconds of its clock, refuses a nonce it has seen in that window, and compares signatures in constant time.

summary.open request

{ "review": "r..." } returns { "url": "http://<name>.lahe.localhost/<path>" }. It runs catalog Open with handoff: false, so it opens at the address the Library would use and never queues a pick-up for an agent (R11). A row that only an agent could serve (PROTO_NOT_OPENABLE) returns { "url": null }, and the app opens the Library instead.

install.json gains a menubar block

{ "app": "<state>/menubar/Lahe.app", "label": "lahe-menubar", "login_item": "...", "source_stamp": "<sha256 of macos/menubar/*>", "built_at": "..." }. Absent when the icon is not installed.

Key Flows

Section 5

The menu stays current

sequenceDiagram
    participant App as Menu bar app
    participant H as Helper
    participant Cache as per-review cache
    loop every 5 seconds, and when the menu opens
        App->>H: GET summary.read (signed proof, no Sec-Fetch headers)
        H->>Cache: stat events.jsonl and review.json per review
        Cache-->>H: rebuild only reviews whose files changed
        H->>H: add window holders, sessions
        H-->>App: summary, signed
        App->>App: drop it unless the signature checks
        App->>App: redraw icon count and menu
    end

The per-review cache keeps a request to a few stat calls per review: the review's events.jsonl, review.json and meta.json, plus the reviewed document itself (so a deleted file drops out) and catalog.json once per request (so a Library rename shows). A same-size rewrite inside one millisecond is caught by comparing size, modified time and inode together. The plan sets the budget (R21) and measures it on Ken's state folder.

Ken reads a reply

sequenceDiagram
    participant Rail as Rail (in the page)
    participant H as Helper
    participant St as Store (events.jsonl, review.json)
    participant App as Menu bar app
    Rail->>Rail: card opened: "1 new" drops, local mark written
    Rail->>H: reply.seen {item, stamp} through the outbox
    H->>St: append; project reply_seen onto the item
    App->>H: summary.read (within 5 s)
    H->>St: that review's files changed: rebuild its summary
    H-->>App: the document's unread count is one lower

The outbox posts at once, and the next summary comes within 5 seconds, so the count drops inside R3's 10 seconds. A question opened and not yet answered is read; the rail still shows it as asking.

Install, rebuild, and Quit

flowchart TD
    Install["lahe install on a Mac<br/>(asks: add the menu bar icon?)"] --> Tools{"xcrun finds swiftc?"}
    Tools -->|"no"| Msg["prints: run xcode-select --install,<br/>then lahe install again.<br/>The rest of install completes."]
    Tools -->|"yes"| Build["swiftc builds Lahe.app<br/>in the state folder"]
    Build --> Item["writes lahe-menubar.plist:<br/>RunAtLoad, restart only on a crash"]
    Item --> Record["install.json records the app<br/>and its source stamp"]

    Timer["helper timer, every 15 s (macOS, installed)"] --> Stamp{"macos/menubar changed<br/>since the recorded stamp?"}
    Stamp -->|"yes"| Rebuild["rebuild in a child process,<br/>swap the app; restart it only<br/>if it was running"]
    Stamp -->|"no"| Idle["nothing"]

    Hide["menu: Hide the icon"] --> Exit["app exits cleanly;<br/>launchd leaves it stopped<br/>until login or lahe menubar show"]
    Stop["menu: Stop Lahe"] --> Mark["write stopped.json,<br/>then launchctl bootout lahe-helper"]
    Mark --> Held["an agent's lahe command sees<br/>stopped.json and fails plainly"]
    Mark --> Back["Start in the menu, lahe install,<br/>or the next login clears it<br/>and loads the item again"]
  • Hide exits with status 0. The login item restarts the app only on a crash (KeepAlive with SuccessfulExit: false), so Hide holds until the next login or lahe menubar show.
  • Stop Lahe holds (R14). The app writes <state>/stopped.json ({"by": "menu bar", "at": "..."}) and then unloads the helper's login item, because a plain kill would be restarted at once. The marker is the hold: startThroughItem, the path every lahe command takes to start an installed helper, refuses while the file exists, with "Ken stopped Lahe from the menu bar at . Click Start in the menu, or run lahe install." and a non-zero exit, so an agent's lahe review fails in one line and starts nothing. Without the marker (an item unloaded by hand, or a stale install), startThroughItem bootstraps the plist and then kickstarts, which today's code cannot do.
  • Start Lahe, shown while stopped with "Stopped by you at ", removes the marker, bootstraps and kickstarts. lahe install removes it too. The helper removes it on its own start, so the login item loading at the next login ends the hold; since nothing else can start the helper while the marker stands, a running helper always means Ken started it.
  • Bootstrap checks the plist first. Before loading lahe-helper.plist, the CLI checks its contents are what login_item.js would write for the recorded install, and refuses with a message to run lahe install if not (SR6).
  • The labels are constants. The app and the CLI use the fixed labels lahe-helper and lahe-menubar and their fixed plist paths; nothing reads a label from install.json to run launchctl (SR6). Tests get their own labels through a seam that stays a constant: the CLI's existing label and home options, and a compile-time -D flag for the app. No test ever loads, stops, rewrites or removes the real labels.
  • A rebuild respects Hide. After swapping in a rebuilt app, the helper restarts it only if launchctl print says it was running. A hidden icon stays hidden through a git pull (R17).
  • The app's Start does not check the plist's contents. It bootstraps only the fixed path in Ken's own ~/Library/LaunchAgents; anything that can write there can already run code at his login, so the check adds nothing for the app. The CLI keeps its check because it also covers a stale install.
  • One build recipe. src/service/menubar.js holds the only build function, the fixed file list and the pinned compiler flags (-swift-version 5, the host architecture, a macOS 13 floor). The build check script calls it.
  • What a rebuild compiles. Only the clone named in install.json, never a worktree; a fixed list of files in macos/menubar/, copied into a fresh temp folder, hashed there, built there with /usr/bin/xcrun swiftc, and renamed into place only on success (SR5).

Alternatives Considered

Section 6

Approaches Ken ruled out in the crucible

A SwiftBar script (no real Lahe icon) and a Dock badge on the Library (he keeps the Dock hidden). See the crucible.

How the app gets its data

  • Chosen: a helper route with the CLI secret. One place computes "waiting on you", with the helper's own projection, liveness, and window holders. Any future tray icon on Linux or Windows reads the same answer.
  • Rejected: the app reads the state folder itself. No route to secure, but the Swift app would reimplement the projection, the liveness test, and the waiting rules in a second language. The two would drift, and a drifted count is the wrong count Ken said is worse than none.
  • Rejected: the app runs lahe status --json every few seconds. No new route, but it starts a Node process every poll (tens of milliseconds and real memory each time, against R21), and lahe status does not know about windows.
  • Rejected: the Library token. It is minted in memory at each helper start and handed only to the Library page, so the app could not get it without a new handout route, which is a new way to leak it.

How the app learns something changed

  • Chosen: poll every 5 seconds, with a per-review cache in the helper. Simple, recovers on its own after the helper restarts, and the cache keeps each poll to a stat per review file. The plan measures it against R21.
  • Rejected for now: a long-poll that the helper answers only on change. Fewer requests, but liveness ages with time (a monitor going stale changes the answer with no event), so the helper would still need its own timer. It can replace polling later without changing the summary's shape.
  • Rejected: rebuilding the Library list per poll. 150 ms warm on Ken's 690 reviews, every 5 seconds, is about 3 percent of a core forever.

When "read" happens

  • Chosen: the rail's own read mark, posted to the store. The card's "1 new" tag already knows exactly which reply Ken opened, and the rule for which replies need reading already exists. The page posts that mark as a reply.seen event, the shape Mark as done uses, and the rule moves to src/shared/ so the helper runs the same one. Nothing new is asked of Ken, and the icon and the rail cannot disagree.
  • Rejected: the page is the focused tab, recorded by the helper. The first draft. It was a second rule for "read", beside the rail's, so the icon could say 2 while the rail said "1 new" on three cards, or the reverse. Ken, in review: use the existing mechanism, do not make a new one. It also needed a new focused claim field and a cap on a new page field (SR3).
  • Rejected: per review. In a folder review, reading one page would clear replies on another (PM review RF1).
  • Rejected: any open window. Ken keeps tabs open for days, so replies would clear the moment they arrived (PM review RF1).

Where the app is built and kept

  • Chosen: built on the Mac by lahe install into the state folder. A program built locally carries no quarantine flag, so no Apple developer account or signing is needed, and nothing binary goes into the repo.
  • Rejected: a ready-built app in the repo or a release. Needs signing and notarization to open without warnings, and a binary in a public repo is hard to review.
  • Rejected: swift LaheMenuBar.swift as a script at each login. Compiles on every start, slow and heavy at login.
  • Rejected: AppleScript or JavaScript for Automation with AppKit. Runs without a compiler, but a long-lived menu bar item from osascript is fragile, shows as "osascript" in Activity Monitor, and is hard to test.

How Stop works

  • Chosen: a stopped.json marker plus unloading the helper's login item. A plain kill is restarted at once by KeepAlive, so the item is unloaded; the marker is what makes the stop hold, because the CLI refuses to load the item again while it stands. Ken, in review: a Stop that restarts itself would make him mad.
  • Rejected: unload the item and let any lahe command load it again. The first draft, with a warning line in the menu. With an agent listening, Stop lasted seconds (SR7, and Ken's answer above).
  • Rejected: a "paused" flag the helper reads at start and then exits. It would fight launchd, which restarts the helper every ten seconds, and agents would see a helper that keeps dying. The marker chosen is read by the CLI before anything is loaded, so launchd never sees a dying helper.

Failure Modes / Edge Cases

Section 7
  • Helper down. Nothing answers on the port. The app shows the not-running look and a Start item (R2). It keeps asking every 5 s, so it recovers on its own.
  • Can't tell (R2). A refused request, a timeout, an answer the app cannot parse, a version mismatch, or the first seconds after the Mac wakes: the app shows the "can't tell" look, never the plain mark and never the last number. After a wake it shows "can't tell" until its first fresh answer.
  • App older than the helper. The app sends the summary_version it was built for. The helper answers a mismatch with 409 SUMMARY_VERSION, and the app shows "can't tell" with "Lahe was updated; rebuilding" (R18). The rebuild timer usually gets there first.
  • App newer than the helper (pulled, helper not yet restarted). The route does not exist, so the request gets a 400 and the app shows "can't tell". The helper's own staleness check replaces it at a quiet moment, as today.
  • Rebuild fails (tools removed, compile error). The helper keeps the old app, records the error in menubar.log, and lahe status names it. It retries only when the source stamp changes again, so a broken build does not compile every 15 s.
  • CLI secret missing or changed. The app rereads the file on each 401. A missing file shows "can't tell" with the reason in the log.
  • An answer the app cannot verify. A missing or wrong signature, from a squatter or a bug, is dropped: "can't tell", logged once per minute at most.
  • Clock skew. The helper and the app read the same Mac clock, so the 30-second window only matters across a sleep. A refused proof after a wake is retried with a fresh timestamp on the next poll.
  • A review whose file is gone, or an unreadable review. Never waiting on you (R7). It can still appear under recent, and Open goes wherever catalog Open sends it, which for a gone file is the plain "file is gone" page.
  • A worktree review. Open follows catalog Open, which already serves a gone worktree file from the main checkout.
  • Many documents waiting. The icon shows the number up to 99, then "99+". The waiting list is not cut (R12); in practice the install cutoff (R4) keeps it short.
  • Two browsers on one review. A mark posted from either lands in the store, and the other adopts it on its next poll, so "1 new" clears in both. A second window refused the rail has no cards to open, so it marks nothing.
  • The page is offline when the card is opened. The mark sits in the outbox like any other record and posts when the helper is back. The count stays up until then, which is the honest answer.
  • An agent while Lahe is stopped. Its lahe command fails with the stop message and exit code 1; a lahe monitor already running sees the helper down and reports it as it does today. The agent tells its human, and only Ken's Start, lahe install or login brings the helper back.
  • Another user on the Mac. Their app reads their own state folder and their own helper port. The secret file is owner-only.
  • Ken renames or retires a review. Retired reviews are dropped from every section. A rename shows on the next summary.

Security & Privacy Notes

Section 8
  • Signed requests, so the secret never travels (SR1). The app does not send the CLI secret. It sends a proof: a timestamp, a random nonce, and HMAC-SHA256 keyed with the secret over the route name, timestamp, nonce, and a hash of the body. The helper accepts a proof within 30 seconds of its own clock and refuses a nonce it has seen in that window. The helper signs its answer the same way, over the nonce and a hash of the response body, and the app drops any answer whose signature does not check and shows "can't tell". A program squatting on the port while the helper is stopped learns one used proof for one route, nothing it can replay or use on site.bind. Node has HMAC in node:crypto and Swift in CryptoKit, so no packages are added. The app connects to 127.0.0.1 at the port in service.json, never localhost.
  • Who can reach the routes. The proof is the control: a web page cannot read the secret file. Two more checks stand behind it. Both routes refuse any request carrying a Sec-Fetch-Site, Sec-Fetch-Mode or Sec-Fetch-Dest header, which current browsers send on every request to a loopback address and the app never sends (SR2). summary.open is a POST with a JSON body, so it also refuses any Origin header. Neither route is a catalog route, the Library host never routes to them, and the Library token is never accepted. The helper's Host check still applies, which stops DNS rebinding.
  • The reply.seen event (SR3). item must be an item of the review the token names, stamp a string of at most 64 characters naming that item's current reply; a malformed event (anything but a string item and a 1 to 64 character stamp, with no other keys) is refused at events.append and never written; a well-formed mark naming another reply lands in the log and is dropped by the projection, like a stale reply, so nothing is projected. It carries no reviewer text. Accepted risk: a page holding a review's token can mark that review's replies read, and only that review's. A page's token already lets it close the item outright with item.closed.
  • What it holds. Titles, ~ paths, counts, times, session names. No comment text, no review tokens, no absolute paths. Same exposure as lahe status, which any process running as Ken can already run.
  • summary.open opens nothing itself (SR4). It returns an address. The app opens it only when it parses as http, with no user or password part, a host of library.lahe.localhost or a valid site name followed by .lahe.localhost, and a port that is absent or equal to the pages port in service.json. It opens the URL rebuilt from those parsed parts, not the original string. The same check applies to library_url. Anything else is dropped and logged. Titles are page-derived: the helper strips control characters and Unicode format characters (such as bidirectional overrides) and caps the length, and the app sets them as plain menu text.
  • Building code on the user's machine. swiftc compiles only the fixed file list from the installed clone, in a fresh temp folder, invoked as an argument array, never through a shell (SR5). The app is not signed. A program built locally carries no quarantine flag, so Gatekeeper does not block it.
  • launchctl calls from the app and CLI use the fixed labels and paths, never values read from a file (SR6).
  • Follow-up, not in this feature: the CLI's two existing secret routes (site.bind, review.retire) still send the raw secret after an unauthenticated /health probe. They should move to the same signed proof. Filed on the board.

Architecture reviews: Menu bar app

Security review

Section 13

Reviewed: 02_architecture_menu_bar_app.md, parts/architecture/alternatives.md, and the brief's requirements R14 to R23. Claims were checked against the code in this worktree (src/shared/protocol.js, src/service/auth.js, src/service/index.js, src/service/routes.js, src/service/sites.js, src/service/catalog_actions.js, src/service/login_item.js, src/service/reviews.js, src/cli/commands/review.js).

Summary

  • No web page can read summary.read or call summary.open. The CLI secret is what stops them, and it holds: no served path reaches the state folder, a page cannot send the secret header across origins without a preflight the helper never approves, and the Host check stops DNS rebinding. One sentence in the design about why is wrong (SR2), but there is no hole there.
  • The one real hole: the app sends the machine-wide CLI secret every 5 seconds to whatever program answers on the helper's port, and "Stop Lahe" leaves that port free for hours. On a Mac with a second account, or with any program that can open a local port but not read Ken's files, that program collects the secret and can then make Ken's helper serve any folder Ken can read (SR1). The fix is small and costs Ken nothing day to day.
  • The new page field on window claims needs a length cap and a check against the review's known pages before it becomes a key in seen.json (SR3).
  • The rest are small tightenings: the app's URL allowlist, which clone gets compiled, and how the app runs launchctl (SR4 to SR6). SR7 is a challenge to what "Stop" promises.

Privacy (focus 5) has no finding: the summary shows less than lahe status already prints (no comment text, ~ paths instead of absolute ones), and only processes that can read the owner-only state folder can fetch it. Those processes can already read everything in it. The one new fact it reveals is which Lahe tab is focused right now, and that is held to the same readers.

SR1. The app hands the CLI secret to anything listening on the helper's port

  • Severity: medium
  • Blocks or trade-off: blocks. It is a real hole on a shared Mac, and the fix does not slow Ken down.
  • Where: Security & Privacy Notes, "Who can read the summary"; Key Flows, "The menu stays current" and "Install, rebuild, and Quit" (Stop).

The attack. The app sends x-lahe-cli-secret on every poll, every 5 seconds, to 127.0.0.1 at the helper's port. It does not check who answers. Any local program can listen on a loopback port above 1024, including programs that cannot read Ken's state folder: another macOS account on the same Mac, a sandboxed App Store app with the network-server permission, or a container started with -p 127.0.0.1:7817:.... Today the helper's port is free only for the seconds of a crash or a staleness restart, because launchd's KeepAlive brings it straight back. "Stop Lahe until next login" changes that. It unloads the login item on purpose, so the port can sit free for hours while the app keeps polling with the secret.

A squatter that collects the secret can then:

  1. Wait for the real helper to come back, and call site.bind with the secret, naming a root such as /Users/<ken>/Documents. rootProblem in src/service/sites.js refuses only the filesystem root and the state folder.
  2. Read files from that site over the pages port. Pages carry no credential, the pages port listens on loopback where every local account can connect, and a non-browser client can send any Host header it likes.
  3. In the meantime, answer the app's polls with made-up counts and made-up summary.open addresses.

The CLI has the same weakness today (src/cli/commands/review.js sends the secret after an unauthenticated /health probe). The original architecture names this residual and narrows it by matching started_at against the owner-only service.json. But started_at is public through /health, so a squatter that polled once while the helper was up can echo it. The app turns a rare, seconds-long window into a constant one.

The change to the design. The secret should never travel. Pick one of these; the first is preferred.

  • Signed requests (preferred). The app sends a proof instead of the secret: a timestamp, a random nonce, and an HMAC-SHA256 keyed with the secret over the route name, timestamp, nonce, and a hash of the body. The helper accepts a proof only within about 30 seconds of its own clock and refuses a repeated nonce. The helper signs its answer the same way (HMAC over the nonce and a hash of the response body), and the app ignores any answer whose signature does not check, showing "can't tell". Node has HMAC in node:crypto and Swift has it in CryptoKit, so the zero-dependency rule holds. A squatter then learns a one-time proof for one route and nothing it can use on site.bind. The CLI's two existing secret routes should move to the same proof in a later change.
  • Minimum, if the plan wants less code. The app sends the secret only when all of these hold: service.json exists, the pid it names is alive and owned by Ken (kill(pid, 0) returns 0, which it does not for another account's process), and /health reports the same started_at as service.json. While the helper is down, or after Stop, the app probes only /health, which carries no credential, and sends nothing secret until those checks pass again. This stops another account and a sandboxed app, but not a same-user process, which is the account boundary the project already accepts.

Either way, the app connects to 127.0.0.1 at the port named in service.json, never to localhost, so it never reaches a different program on ::1. The plan should carry a test row: a fake server on the port receives no secret.

SR2. "A browser always sends Origin" is not true for GET, so the secret is the only control on summary.read

  • Severity: low
  • Blocks or trade-off: neither. It is a design-text fix and a cheap second check, at no cost to Ken.
  • Where: Security & Privacy Notes, "Who can read the summary".

The failure. site.bind and review.retire are POSTs, and browsers do send Origin on every POST, so "refuse any Origin" is a real second check there. summary.read is the first GET on this auth mode. Browsers do not send Origin on a no-cors GET, on a navigation, or on an <img> or <script> load. So a page can reach the route with no Origin header. It cannot send the secret header that way, and the helper sends no CORS headers, so it reads nothing. The secret still holds. But the design's reason is wrong, and a plan that tests only "a request with Origin is refused" would pass while proving nothing about GET.

The change to the design.

  • Correct the sentence: the secret is the control, and Origin refusal is a second check that only applies to POST.
  • Add a second check that does apply to GET: refuse any request carrying a Sec-Fetch-Site, Sec-Fetch-Mode or Sec-Fetch-Dest header. Current Chrome, Firefox and Safari send these on every request to a loopback address. URLSession and Node's fetch send none.
  • Make summary.open a POST with a JSON body, so it gets the Origin check too and no simple request can reach it.
  • Keep both routes out of the Library's catalog routes and out of routes.isCatalogPath, so the Library host never routes to them, and never accept the Library token on them.
  • Plan test rows: a no-Origin GET with Sec-Fetch headers is refused; a request with the Library token is refused; a request to the summary path at library.lahe.localhost is refused.

SR3. The page field needs bounds before it becomes a key in seen.json

  • Severity: medium
  • Blocks or trade-off: blocks, in the sense that the plan must include the checks. They cost Ken nothing.
  • Where: Data / State Changes, seen.json; Failure Modes, "Two windows on one review".

What is already safe. A window claim is checked against the review's own token and origin list (protocol.checkRequest). So a page can only ever touch seen marks for its own review. It cannot clear Ken's count on another review.

The failures.

  1. Unbounded writes. page is a string the page chooses. The helper accepts bodies up to 8 MB (MAX_BODY_BYTES in src/service/index.js). The design says the helper writes only when "a focused window's time passes the newest agent reply on that page". If an unknown page falls back to "the newest reply on the review", or the mark is stored before that test, every distinct page value adds a key. A script can send thousands of claims with different long strings and grow seen.json without limit. That file is read on every summary.
  2. Object keys. reviews[id][page] as a plain object lets page be __proto__, constructor or toString. A lookup then returns a function, not a time, and the count for that review goes wrong.
  3. Anyone holding the review token can clear that review's unseen answers. quiet: false is the page's own claim. The design also counts a refused claim (a second window) as looking. Anything that can read the token from the page's script tag can send quiet: false with any page, or with no page at all, which marks every page. That includes a third-party script on a reviewed page, such as a local app under review that loads analytics. Ken then misses an agent's answer on that review. Open questions are not affected, because rule 1 does not use seen marks.

The change to the design.

  • page must be a string of at most 1024 characters, normalized the same way the helper names pages when it records replies. A claim with a bad page is treated as having none.
  • Look page up in the set of pages that carry an agent reply on this review, using Map or Object.create(null) and own-property checks. If it is not in that set, write nothing. That bounds seen.json by pages with replies, not by what pages send.
  • State item 3 as an accepted residual risk in the design: a token holder can clear its own review's unseen answers, and nothing else. Making a refused claim count is a fair trade for two-window use. Ken should know it is a trade.
  • Plan test rows: a 1 MB page writes nothing; __proto__ writes nothing and does not change any count; a page path with no replies writes nothing; review A's token cannot change review B's marks.

SR4. The app's URL allowlist is wider than anything the helper returns

  • Severity: low
  • Blocks or trade-off: neither. The helper never returns the extra forms, so tightening costs nothing.
  • Where: Security & Privacy Notes, "summary.open opens nothing itself".

The failure. catalog Open always builds its address with protocol.siteOrigin, which gives http://<name>.lahe.localhost with either no port (the port-80 forward) or the pages port (catalog_sites.addressOf). The Library address is library.lahe.localhost. The allowlist also lets through <name>.lahe, 127.0.0.1 and localhost at any port. If the helper is ever impersonated (SR1) or a bug puts the wrong value there, the app would open, say, http://localhost:631/... or a local dev server's endpoint that acts on a GET. <name>.lahe without the verified resolver goes to the system's DNS, which on some networks answers for unknown names.

The change to the design.

  • Accept only scheme http; a host of library.lahe.localhost or one matching the site-name rule followed by .lahe.localhost; a port that is absent or equal to the pages port in service.json; no user or password part.
  • Parse with URLComponents and open the URL rebuilt from those parts, not the original string, so the app and the browser cannot read the same string two ways.
  • Apply the same check to library_url from the summary.
  • Titles: besides control characters, strip Unicode format characters (the bidirectional overrides such as U+202E), and cap the length, so a page title cannot make one row look like another document.

SR5. Which clone gets compiled, and what exactly gets compiled, should be pinned

  • Severity: low
  • Blocks or trade-off: neither. It needs a few sentences in the design and a test row.
  • Where: Components (src/service/menubar.js, src/cli/commands/menubar.js); Security & Privacy Notes, "Building code on the user's machine"; Install, rebuild flow.

The failure. The helper compiles native code that launchd then starts at every login. Using argument arrays with no shell is right. Three gaps remain:

  1. The design does not say which clone lahe menubar rebuild compiles. If it compiles the clone the CLI runs from, then an agent running it from a worktree installs that worktree's unreviewed Swift as Ken's login item.
  2. "Files in macos/menubar/" read as a glob would also compile any extra .swift file, or a symlink to a file outside the folder.
  3. The helper hashes the folder and then compiles it. If the files change in between, the recorded stamp describes code that was not built. A half-written app can also be started by launchd if the build writes in place.

The change to the design.

  • Only ever compile from install.json's clone, the same clone the helper's login item runs. The helper timer and lahe menubar rebuild both follow it, never the CLI's own clone. This matches how sourceRoots already judges staleness.
  • Compile a fixed list of file names, and refuse symlinks.
  • Copy those files into a fresh build folder inside the state folder, hash the copies, compile the copies, build to Lahe.app.new, then rename it over Lahe.app and restart the app. The stamp then always matches the binary.
  • Run /usr/bin/xcrun swiftc by absolute path with a small fixed environment, not whatever PATH launchd gave the helper.
  • Keep the app inside the owner-only state folder, as designed. It must never move somewhere another account can write.

SR6. The app should not read launchctl targets from install.json

  • Severity: low
  • Blocks or trade-off: neither.
  • Where: Security & Privacy Notes, "launchctl calls from the app"; Key Flows, Stop and Start; src/service/login_item.js startThroughItem.

The failure. The labels are fixed: lahe-helper (login_item.LABEL) and lahe-menubar. Reading them, and the login_item path in the new menubar block, from install.json adds a file to trust for no gain. The new bootstrap step loads whatever plist sits at the path it is given. Only a same-user process can change either file, so this is defense in depth and not a hole.

The change to the design.

  • The app uses the two labels as constants in its Swift source, and runs /usr/bin/launchctl by absolute path with an argument array.
  • The bootstrap step, in the app and in startThroughItem, builds the plist path from the home folder plus the checked label, the way describe() already does. It never reads the path from install.json.
  • Before bootstrapping, check that the plist's contents are what describe() would write for this install. If they differ, refuse, and say "run lahe install again".

SR7. "Stop Lahe" is undone by the next agent command (challenge)

  • Severity: low
  • Kind: challenge to R14, which Ken asked for
  • Blocks or trade-off: trade-off for Ken.
  • Where: Key Flows, "Stop Lahe"; brief R14.

The failure. With bootstrap-before-kickstart, any lahe command that needs the helper loads it again, and a live monitor runs such commands all the time. So Stop may last only seconds. R14's help line says agents will start it again, so this is known. The security angle: people reach for a stop control when something looks wrong, or before sharing their screen. A stop that automation quietly reverses fails open, and the stopped window is also the window SR1 is about.

The change to the design, if Ken wants it. Stop writes a stopped_until_login marker in the state folder (cleared by the login item at load). While it is there, agent commands do not bootstrap the helper on their own. They print a line telling the agent the human stopped Lahe. Only Start in the menu, or a command Ken runs, loads it again. If Ken prefers today's behavior, the menu line should say plainly that a running agent will start Lahe again within seconds.
