Summary

Section 1

An agent writing a page for Ken can put a choice on it: a short question with two or more answers drawn as buttons. Ken clicks one. The click reaches the agent as its own record, naming which choice and which answer, so two groups that both offer "Promote" can never be confused. Presses made close together reach the agent together. The page shows what was chosen, and once the agent has acted the decision lives in the document's own source, so the page shows it with no Lahe running. This works on documents only: pages the Lahe program serves itself, rendered from Markdown or written as HTML by an agent. A page on someone else's dev server gets nothing new.

Problem, User, and Context

Section 2

Ken, in his words: the job is to answer a question from the agent quickly and easily, and the user who matters most is the agent writing the page: instructions must be clear and communication must be good.

Today an agent that needs nineteen verdicts writes a page with nineteen recommendations and Ken answers each one by selecting text, pressing Cmd-Shift-C, typing, and pressing Cmd-Enter. The lesson-queue agent invented a shortcut on its own, "one comment saying all as recommended is enough", because the real thing was missing. Every exception to that shortcut arrives as prose the agent can misread.

The scene is a laptop, the page in a browser tab, amid eighteen other things.

Prior work: the crucible summary and the questions page with Ken's edits folded in. The standard docs that bear on this: the product brief (the record is the truth; don't waste tokens; don't cause no-ops), the style guide (option cards with a Recommended badge are the component for a choice), the brand doc (which promises interactive modules), and the architecture doc, which says a new kind of record changes that doc first.

flowchart TD
  A[Agent writes a page with a choice group per decision] --> B[Ken clicks answers, one group after another]
  B --> C[The presses are sent as their own records, together when made close together]
  C --> D[The agent reads them in the drain: which group, which answer]
  D --> E[The agent acts, writes each decision into the source, and replies on each thread]
  E --> F[The page shows every decision, from the file, with or without Lahe]

Non-Goals

Section 3

Non-goals

  • Not on live sites. A page served from someone else's dev server (the lahe add path) is untouched: no click is claimed there, and a choice group on such a page is inert content.
  • Not a general form. No free-text field, slider, ranking or multi-select in this cut. A question with a free answer stays a comment.
  • Not a page-level "all as recommended" switch. An agent that wants one writes one more choice group and says in its question what it covers.
  • Not a change to how comments, edits or free writing work. A comment left on a choice group is an ordinary comment.
  • Not an agent pressing a button on the reviewer's behalf.
  • Not an automatic report to the agent when it wrote a broken group. The reviewer sees the problem in the rail and says so. Deferred; see the questions leaf.
  • Not mobile. Lahe has no mobile story and this feature does not start one.

Solution Outline

Section 4

The agent writes a choice group into the page the way it writes any other house component: a question, two or more answers, and the one it recommends marked. On a document page the group draws as buttons grown out of the option-card component. Ken clicks an answer. There is no draft and no confirm: the click is the commit. The press is a record like any other, so it survives a reload, a closed tab and a Lahe program that is down. Presses made within a few seconds of each other travel to the Lahe program together and wake the agent once. In the agent's drain each arrives as data that names the group and the answer, with nothing to parse. The agent acts, writes the decision into the page's source, and replies on the thread as it does for a comment. From then on the document itself carries the decision.

Requirements

Section 5

Authoring

Requirement

R1: An agent can put a choice group on a document page in a few lines, written into the page's Markdown or HTML: a question, two or more answers, and optionally which one it recommends. The lahe skill and the component catalog teach the block. Checked by the skill eval: a fresh agent given only the skill text and the catalog writes a group that arms on its first try.

R2: A choice group is a house component, grown out of option cards: the recommended answer, when there is one, carries the Recommended badge, and nothing has a colored edge. It reads as part of the document, in the document's style.

R3: A page with no choice groups renders and behaves exactly as it does today.

R4: A group an agent got wrong (no id, a malformed id or answer, two groups with the same id) draws as plain content, not live buttons, and the rail says which group and why before anything can be pressed.

Pressing

Requirement

R5: A click on an answer sends the press at once. No draft state, no Cmd-Enter. The page shows which answer was pressed.

R6: One answer per group. Pressing a different answer before the agent has replied changes the choice, and the agent sees only the latest.

R7: After the agent has handled a press, pressing again on the same group starts a new thread. The agent undoes what the earlier answer asked for, does what the new one asks, and says both on the thread.

R8: A press is a record like any comment or edit: kept in the browser as it is made, sent to the Lahe program, shown as a thread in the rail, and preserved across a reload, a closed tab and a program restart.

R9: The group shows its state on the page in the rail's own words, which are the brand's three thread states plus the not-stored case. Kept in this browser (the Lahe program has not stored it yet). Open (stored and waiting on the agent, including after the agent said no, whose reason is on the thread). Question (the agent asked something on the thread). Done (the agent acted, or the reviewer marked it done). The state survives a reload and the agent's rebuild.

R10: When a rebuild moves a group, its state follows it. When a rebuild removes a group while its press is open, the press stays on its rail thread and the thread says the group is gone. A press never attaches to a different group.

R11: On every page, Lahe responds only to clicks on a choice group's own buttons. Only a page the Lahe program serves itself (rendered Markdown, an HTML page in a served folder, a lahe write page) carries live groups. On a page from another dev server the layer claims no click, and every link, form, button and script behaves as before.

Reaching the agent

Requirement

R12: A press reaches the agent in the drain as data: which group, which answer, the group's question and the heading it sits under. The agent reads fields and parses nothing. Two groups that offer the same answers are never confused.

R13: Presses made within a few seconds of each other reach the Lahe program together. The agent wakes once per batch of work that landed since it last looked, never once per press, so clearing the nineteen-lesson queue by clicking costs a handful of wakes at most, one per stretch the agent spends working. The count is measured with R15.

R14: The agent answers a press the way it answers a comment: handled, not handled with a reason, or a question. The reply shows on the thread, and Mark as done works on it.

R15: Clearing the lesson queue with presses costs fewer tokens on the agent's side than clearing it with one comment per lesson. Measured on the real page, the way the lean-agent-output feature measured one comment.

R16: The page check never holds a press for words that were never typed on the page. A handled reply on a press retires it.

Keeping the decision

Requirement

R17: Handling a press includes writing the decision into the page's source. After that, the page shows the chosen answer on a fresh load with no rail and no Lahe program. Until then, the layer shows it from the record.

Agents learning it

Requirement

R18: The lahe skill's components table and the component catalog gain the choice group, and the contract text in review.json says how a press appears in the drain, how to answer it and that handling includes the source write-back. The skill edit is made with the skill-creator skill, and the skill, the contract and its copies ship together, as CLAUDE.md requires.

R19: The first working page shown to Ken, before any PR gate, is the lesson queue rebuilt with a real choice group per lesson, with the rail live.

AI Behavior

Section 6
  • When to use which component. Option cards describe alternatives: a name, a line or two, the costs, a Recommended badge. A choice group collects the answer. A page that asks a question uses a choice group for the answer and, when the alternatives need explaining, option cards above it. A page that only records a decision already made uses neither.
  • When a group fits. An agent offers a choice group whenever it can name every answer in advance and will act on the answer: promote or discard, approve or hold, A or B. When the answer is free text, it asks in prose and expects a comment. A group needs no recommendation when the agent has none.
  • On a press. The agent does what the answer says, writes the decision into the source, and replies handled in one sentence about the document, the way the skill already asks for comments. A press that needs more from the reviewer gets a question on its thread, not a new page.
  • A changed mind. A new press on a group the agent already handled is a new thread. The agent undoes what the earlier answer asked for where that is possible, does the new one, and says both. A press that arrives while the agent is mid-task is handled on the next drain, never dropped.
  • A comment on a group is an ordinary comment and is answered as one.
  • An agent never presses a button itself and never writes a press into the store by hand.

How we know it worked

Section 7
  • Ken clears a lesson queue by clicking, with no comment typed, and every lesson ends up where he clicked it.
  • A week of decision pages with no wrong answer reaching an agent and no "which one did you mean" question back.
  • The token comparison in R15 shows presses cheaper than comments on the same page.

UX Notes

Section 8
  • The group's state is visible on the page (R9), and the rail's thread for it shows the question, the answer and the state chip like a comment card. The answer on the card is not editable; changing it is a new press.
  • Buttons are real buttons: keyboard reachable, with the house focus ring.
  • Documents are light only, so the component needs no dark twin on the page. The rail card follows the rail's own scheme as every card does.
  • The brand doc's word list gains the term for this component so the rail, the skill and the docs call it one thing.
  • A visual change ships with a screenshot from the built page, after the test that proves it.

Analytics / Logging

Section 9

No new analytics. A press is an item in the review's event log and in review.json like every other record, which is the whole audit trail. One measurement script, for R15, records the drain cost of clearing the lesson queue by presses against clearing it by comments.

Rollout / Flags

Section 10

No flag. A page without a choice group is unchanged (R3). A new record kind reaches review.json, so an agent on an older copy of the skill sees a kind it was not told about; the contract text ships in the same change and npm run install-skills brings the skill up to date. The architecture doc was changed first, as its own rule requires.

Questions and Decisions

Section 11

No open questions. Ken said the rest should be straightforward and he does not need to be asked, so every call below was made by the brief; he can overrule any of them in review.

Settled with Ken in the crucible (details on the questions page):

  • Approach B, a choice record. Ken: "let's do this", and "I think this might be better for token management as well."
  • Documents only, never on a live site. Ken: "just don't do it on live sites. only docs."
  • The job, in his words: "Answer a question from the agent quickly and easily."
  • Who it is for, in his words: "Agent writing the page: instructions must be clear and communication must be good."
  • How identity is carried is architecture, not brief. Ken on the premise that spelled out an id and a uniqueness check: "this is architecture."
  • No "answer in words" button. Highlighting and commenting is always available, so it needs no saying.
  • The clickable choice grows out of the option-card component. Ken: "love this."
  • Agents learn to author it from the lahe skill and the component catalog, and that skill change is made with the skill-creator skill.

Chosen by the brief, for Ken to overrule in review:

  • A click is a commit (R5). There is no draft state for a press; it is sent the moment it is made.
  • One answer per group (R6). A group is a single choice among its buttons. A page that needs several ticks uses several groups.
  • A press after the agent has handled the group is a new thread, not a reopen (R7). The old thread stays as the record of the earlier decision. The agent undoes and redoes, and says both.
  • No page-level "all as recommended" switch. An agent that wants one writes one more group and says in its question what it covers. Nothing special is built.
  • The decision lives in the file (R17). Handling a press includes writing it into the source, so the document shows its decisions with no Lahe present.
  • Presses close together travel together (R13). The few-second window is the architecture's to set.
  • A broken group is shown to the reviewer, not reported to the agent (R4). The rail names the group and the reason. An automatic message to the agent was deferred: it would be a new agent-facing channel for an authoring mistake the reviewer can report in one comment. Revisit if agents keep getting the block wrong.

PM Review (Round 1)

Section 13

Reviewer: PM persona. Brief read: 01_brief_choice_buttons.md, with the questions part, the crucible summary, the crucible questions page, the product brief, brand doc, style guide, the lahe skill's "Writing a page for someone to read", and the accepted menu bar brief as the bar.

Verdict. The brief is faithful to Ken. It keeps every decision he made (approach B, documents only, no "answer in words" button, grown out of option cards, identity left to the architecture, taught through the skill). The problem is stated in his words, and the requirements stay at product level. What is missing is the edges a builder would otherwise invent: what the page shows in each state, what a quick run of presses costs, what happens when Ken changes his mind after the agent already acted, and what happens when a rebuild moves or removes a group. Each one can be settled by the brief writer without asking Ken.

Not found: docs/ongoing/diagrams/INDEX.md does not exist in this repo. The diagrams live in docs/diagrams/ with a README, and none of them bears on a brief-level judgment here.

RF1. A run of presses could wake the agent once per press

  • severity: important
  • kind: risk
  • where: R11 (a press costs fewer tokens than a comment), line 90; Summary, line 5
  • what: R11 measures the size of one press in the drain, but the real cost of a queue is the number of agent turns, and the monitor wakes the agent once per item.
  • why: Ken picked approach B partly because "I think this might be better for token management as well." On the lesson queue he will press nineteen buttons in under a minute. If each press is its own wake, the agent rereads its context up to nineteen times, which costs more than one comment per lesson ever did. That breaks the product brief's "Don't waste tokens" and "Don't cause no-ops" principles.
  • fix: Add a requirement about the outcome, not the mechanism: "Presses made close together reach the agent together. Clearing a page of N choices costs about as many agent turns as one comment, not N." Change R11 so it measures the cost of clearing the whole lesson queue with presses against the same queue cleared with comments. "Sent at once" can stay true for the helper; how the wake waits is the architecture's call.

RF2. Changing your mind after the agent already acted is not covered

  • severity: important
  • kind: defect
  • where: R5 (one answer per group, a later press replaces an earlier one), line 64; R6 (a press after handling starts a new thread), line 68; AI Behavior, lines 115 to 117
  • what: R5 gives Ken a window to change his mind "before the agent has replied", but the agent wakes at once, so that window is often a few seconds, and nothing says what the agent does when the second press arrives after it already acted on the first.
  • why: There is no confirm step, so a misclick on "Discard" among nineteen rows is sent and acted on. Ken's natural fix is to press "Promote". If the agent treats that as a fresh request without undoing the discard, the lesson is gone and nobody notices. It also leaves a race: the agent may have read the first press and started work when the second lands.
  • fix: Add to AI Behavior: "When a later press on the same group reverses an earlier one, the agent undoes what it did for the earlier answer, then does the new one, and says both on the thread." Add to R5 that the agent acts on the latest answer it can see when it starts, and that a press arriving mid-work is handled on the next turn, never dropped.

RF3. What the page shows for a press, in each state, is undefined

  • severity: important
  • kind: defect
  • where: R4 (the page shows which answer was pressed and that it was sent), line 60; R7 (kept in the browser, survives a helper restart), line 72; R13 (shows the answer once handled), line 100; UX Notes, line 121
  • what: The brief names only two looks, "sent" and "handled", but its own requirements create at least four more: kept in the browser because the Lahe program is down, waiting with no agent listening, answered "not handled", and answered with a question.
  • why: "Sent" is untrue when the Lahe program is down (R7 says the press is only kept in the browser then). "Sent" with no agent listening reads as "done" to someone amid eighteen other things, and the verdict sits unread. A builder will invent these looks and their words, and the brand doc says the interface reassures with facts ("Kept in this browser"), not guesses.
  • fix: List the states once, in the Requirements, as what Ken sees on the page: pressed and kept in this browser; delivered, waiting on the agent; the agent asked a question; not handled, with the reason on the thread; done. Say the state words match the rail's thread states (Done, Open, Question) from the brand doc's words table, and that the rail's existing "no agent listening" line covers a press the same way it covers a comment. Add the word Ken sees for a press (for example "your choice") to the brand doc's "Words we use" table in the same change.

RF4. A rebuild that removes, moves or rewrites a group has no rule

  • severity: important
  • kind: defect
  • where: R7, line 72 ("The pressed state on the page survives a reload and the agent's rebuild"); R13, line 100
  • what: R7 assumes the group is still there after a rebuild, but agents routinely change the page around a decision.
  • why: The skill tells agents to "Keep the top current": when an item is settled, move it out of the top into a Decisions section. So the normal case after a press is that the agent moves or rewrites the group. A builder has to guess whether the pressed state follows a moved group, what happens if the agent renames "Promote" to "Accept", and where a press goes when its group is deleted. The worst guess, a press attaching to a different group, is exactly the confusion Ken asked this feature to prevent.
  • fix: Add one requirement: "A pressed state follows its group when the agent moves it. If a rebuild removes the group or the pressed answer, the press stays on its thread in the rail and shows nowhere on the page. A press never attaches to another group or another answer." Add a line to AI Behavior about how a handled group should be moved under "Keep the top current", so the skill and this feature agree.

RF5. An agent that writes two colliding groups, or a broken one, finds out too late

  • severity: important
  • kind: risk
  • where: R1 (an agent can write a group in a few lines), line 46; R9 (two groups that offer the same answers are never confused), line 82
  • what: R9 promises no confusion between groups, but nothing says what happens when the agent itself writes two groups that cannot be told apart (the copy-paste case on a nineteen-row page), or a group with one answer or no question.
  • why: Ken named the agent writing the page as the user who matters most. If a broken group renders as working buttons, the reviewer is the one who discovers the bug, after pressing. That is the trust failure the crucible's case against building warned about: "a feature that gets identity wrong once teaches him not to trust it."
  • fix: Add a requirement stated as an outcome: "A group the press could be confused with, or a group that is not well formed, is reported to the agent before the reviewer can press it, and draws on the page as plain content rather than live buttons." Leave how and when it is checked to the architecture.

RF6. The AI Behavior section does not tell an agent when to use plain option cards

  • severity: important
  • kind: defect
  • where: AI Behavior, lines 113 to 117; R14 (the skill and catalog gain the choice group), line 106
  • what: The skill's components table today says "A choice for the reader: option cards", and the brief adds a clickable sibling without saying which one an agent picks.
  • why: Ken's user statement is "instructions must be clear and communication must be good." With two components for "a choice", agents will split: some keep writing option cards for decisions (Ken is back to highlight, comment, submit), and some turn every comparison into buttons. Two smaller gaps sit in the same section. It does not say what the agent does when Ken comments on a group instead of pressing it, for example "Promote, but rename it". It also does not say whether a recommendation is required, though R1 implies it is.
  • fix: Add three lines to AI Behavior. First: "Use a choice group when you need the reader's answer and can name every answer. Use option cards when you are showing options to compare and the answer is free, or when the choice needs more than a button label to explain." Second: "A comment on a group is that group's answer. Handle it like a press, and the group may stay unpressed." Third: "Mark a recommendation when you have one. A group without one is allowed." Then say in R14 that the skill's components table row for "A choice for the reader" changes to match.

RF7. R13 leaves open whether the agent has a job in keeping the decision

  • severity: important
  • kind: risk
  • where: R13 (the page keeps showing the chosen answer on a fresh load), line 100
  • what: "How the document carries it is for the architecture" hides a product choice: whether the decision lives only in Lahe's records or in the file itself, which the crucible suggested borrowing from approach C.
  • why: If the architecture puts the answer into the source, the agent has a new step on every press, and the AI Behavior section does not mention it. If it lives only in Lahe's records, a reader opening the file in another tool or after the review ends sees no decision. Each is defensible, but the brief has to say which outcome Ken gets, or the architecture is choosing what the product promises.
  • fix: State the outcome in R13 in one sentence. For example: "After the review ends, opening the document address still shows the chosen answer." Or say it is only while the review is live. If the chosen outcome needs the agent to write anything, add that step to AI Behavior.

Q2 becomes "No page-wide 'all as recommended' choice in this cut. A note on the page still works for that."
