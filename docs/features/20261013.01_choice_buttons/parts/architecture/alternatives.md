Each entry names what was chosen, what was rejected, and why. Read this before deviating.

- **A `choice` field, not words in `note`.** A press could have been a comment whose note reads "promote". Rejected: `note` is free text, the agent would parse it, and the identity would ride on the anchor. The `choice` field is two bounded tokens the agent reads as data, and the group name is the agent's own.
- **`data-choice`, not `data-lahe-choice`.** The tool strips every `data-lahe-` attribute from captured markup and from the element descriptions agents get, so a group name under that prefix would vanish from an edit made near it. The layer's own state attributes stay under `data-lahe-` for exactly that reason: they are the tool's, not the document's.
- **An explicit `data-lahe-document` attribute, not inference from the script src.** The layer could tell a helper-served page by whether the tag's src is the library path on the page's own origin. Rejected: an inference from a URL shape is a rule nobody can read, and a serving change would silently flip it. One attribute the helper adds to its own responses is testable and visible.
- **A rung in the anchor engine, not a separate re-mark pass.** A pass of its own would have to re-implement lost-marking (the persisted `region.lost`, the card badge, and clearing both), which is where the 2026-08-17 stuck-badge bug came from. One rung keyed on the record's kind keeps D9 in one engine, and replay, lost-marking and "show me where" work unchanged.
- **The agent writes the decision into the source; the layer only paints the DOM.** The layer could write `data-chosen` into the page itself, but a rebuild drops it. Having the agent carry it into the source is the same move the stamp round makes with `data-lahe-id`, keeps the record as the truth, and lets a page show its decisions with no Lahe present (the one thing worth taking from the checkbox approach).
- **The hold in `splitForFloor`, not a timer in `choices.js`.** The outbox is flushed by the poll loop about once a second and `scheduleFlush` never pushes an armed timer back, so a sliding window built from timers would not hold. The one place that already holds events back is `splitForFloor`, and a cap keeps steady clicking from holding work for minutes, as the draft floor's spec required.
- **Accept the wake count and measure it, rather than change the monitor.** The monitor polls every 15 seconds and exits on the first poll with new work, so a batch is one wake and a clicking session is one wake per agent cycle. A quiet spell in the monitor would bound it further and would cover comments too, but it changes a loop every host shares; that is Ken's call and it is on the board.
- **No new lifecycle state.** A "pressed" state was considered. Rejected: a press is a draft that is ready in the same tick, which the table already allows, and the reword and reopen paths already model changing one's mind.
- **A raw HTML block, not a Markdown shorthand.** A fenced `::: choice` block the renderer turns into the component would be shorter to write. Rejected for now: marked passes HTML through already, the same block works on an agent's HTML page, and the renderer stays untouched. A shorthand can be added later without changing the record.
- **Real `button` elements, not styled divs.** Keyboard, focus ring and screen readers come free. `type="button"` keeps them out of any form.
- **Approach A (a button that posts a comment) and approach C (task-list checkboxes)** were rejected in [the crucible](../../00_crucible_choice_buttons.md): A fails on repeated buttons, C is Markdown-only and not exclusive.
