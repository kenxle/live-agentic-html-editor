Summary

Every document Lahe serves gets an address that keeps working, like http://20261011-02-stable-addresses.lahe.localhost:7817/01_brief_stable_addresses.md. A tab left open overnight, a history entry, or a bookmark loads the page, with no agent running. The address names the folder and the file, so a tab says what it is. One always-on Lahe server, started at login, answers for every document on one port. Each folder's name is its own browser origin, so documents stay walled off from each other as they are today.

Problem, User, and Context

Ken reads nearly every plan, brief, and report through Lahe, and keeps many Lahe tabs open across days. Today those tabs die. Each document is served by a small server that an agent session owns. The server stops two minutes after its last window closes, or when the session closes, and the helper itself stops once nothing is open. After that, nothing answers at the address. The browser shows its own "can't connect" page, and Lahe never sees the request.

So Ken cannot use browser history or bookmarks to get back to a document. He routes through the Library or asks an agent, and he reads bare 127.0.0.1:56055 addresses trying to work out what a dead tab was. In his words: "it's the constant dead tabs that i run into and have to try and decipher what they are by the url."

    Up -->|"usually not"| Dead["browser: can't connect<br/>address says only 127.0.0.1:56055"]

The settled decisions, and the reasoning Ken reviewed, are on the decisions page. Prior work: the crucible; option D on the Library ideas page, dropped on 2026-09-22 and revisited here.

What "a document" means here: one file on disk. The same file gets the same address every time it is served, in any review. The address has two parts: a name for the folder Lahe serves the file from, and the file's path in that folder.

Related bulletin rows: this feature closes or changes four open rows:

  • LAHE-static-server-host-check (filed twice): page servers do not check the Host header. The always-on server checks it (requirement 10, only this computer can reach it).
  • LAHE-idle-battery-cost: finished sessions' page servers keep running. There are no per-session page servers after this feature. Live tabs still poll, which requirement 11 (light when idle) measures.
  • LAHE-library-quiet-close-no-self-stop: the helper stays up after a Library close. The server is meant to stay up now, so the row closes.
  • LAHE-title-recorded-late: titles are only recorded after a comment. Names come from file names (requirement 3), so this row is not needed for addresses.

The user is Ken today, on a Mac laptop. Lahe is public, and other people run it on Mac, Linux, and Windows, so nothing here may be Mac-only in the core.

Non-Goals

  • Not reviving tabs opened before this feature ships. Their addresses used ports nothing will listen on again. The Library's Open moves them to a stable address.
  • Not stable addresses for pages served by a server Lahe does not own, like an app's own dev server. Lahe reviews those where they run.
  • Not a better story for deleted or moved files, beyond requirement 13 (worktree copies) and a plain "this file is gone" page.
  • Not the Mac menu-bar companion app. It is its own follow-up.
  • Not a single-file build of Lahe that runs without Node. That stays open for later.
  • Not a change to how agents run a review: lahe review, the monitor, draining, replying, and takeover work as they do now. What changes underneath is who keeps pages served (the always-on server, not the session) and when the server stops (it does not, once installed).
  • Not a change of address when a Library row is renamed. The address comes from the file name and stays put.
  • Not new outside packages. The zero-runtime-dependency rule holds; the install step is for setup only.

Solution Outline

  1. One always-on Lahe server. It starts when Ken logs in and restarts if it stops. It answers for every document Lahe serves, whether or not an agent is working on it.
  2. An address per document. The first time Lahe serves from a folder, the folder gets a short name from its own name. The name stays the same after that. A document's address is http://<folder name>.lahe.localhost:<port>/<file>.
  3. One shared port. Every document uses the same port. The server reads the name in the address to know which document was asked for.
  4. .lahe.localhost everywhere, with .lahe as a Mac option. Every browser already sends .localhost names to this computer, with no setup. On a Mac, an optional setup step, run once with an admin password, also makes the shorter .lahe ending work. Which ending lahe review prints is the open decision in the questions below.
  5. Agents keep working the same way. lahe review prints the stable address. Sessions, the monitor, and takeover are unchanged. A comment left on a page with no agent waits in the store, as it does after the Library's Open today.

Requirements

R1. An old address keeps working. Once Lahe is installed, a document's address loads its page after the agent session closes, after any idle time, after the server restarts, and after a reboot. Nobody has to run a command first. Without the install, see requirement 7 (starts at login).

R2. A page loads with no agent. Visiting an address with no agent attached shows the page and lets Ken comment. Comments wait for an agent, and the rail's "No agent watching" line says so, as it does after the Library's Open today.

R3. The address names the folder and the file. The folder's name, in lowercase words joined by dashes, comes first: 20261011.02_stable_addresses becomes 20261011-02-stable-addresses. The file's path in that folder comes after the port, as it does today. Two different folders with the same name get a short tag from their parent folder, like notes-personal. A folder keeps its name once it has one. Serving the same file again, in any review, gives the same address.

R4. Documents stay walled off. Each folder's name is its own browser origin, the same unit a page server is today. JavaScript on a page in one folder cannot read pages, comment keys, or drafts from another folder, and cannot use the Library's controls. Files in the same folder share an origin, as they do today. Hidden files are never served.

R5. One port for every document. All documents share one port: the helper's own port, 7817 unless the install picks another. It is kept away from common dev-server ports. If something else holds that port when the server starts, lahe review, lahe status, and the log say so plainly, naming the port, rather than moving documents to random ports.

R6. .lahe.localhost works everywhere; .lahe is a guarded Mac option. Every name answers at .lahe.localhost on every system, with no setup, so those addresses keep working through install, uninstall, and any setup failure. On macOS, an optional setup (an admin password, once at setup) makes the same names answer at .lahe too. Lahe answers .lahe only after it has checked that its own setup is the one answering .lahe lookups on this machine. lahe status says which ending lahe review prints, and why.

R7. Starts at login on every system. An install command sets the server to start at login and restart if it stops, on macOS, Linux, and Windows. An uninstall command removes that, and removes the .lahe setup. Running Lahe from a clone without installing still works: lahe review starts the server as it does today, and a document's address stays the same. Its old tabs load again whenever the server is running, and are dead while it is not.

R8. Every existing document can get an address. Any review already in the state folder, served by Lahe, gets its stable address the next time it is served: by lahe review, or by the Library's Open. The Library's rows link to stable addresses.

R8a. Links between pages keep working. A link from one Lahe page to another file opens that file, with the rail it gets today. Images, styles, and scripts a page loads by relative path keep loading, as they do today.

R9. Drafts come back. Unsent drafts saved on a document's page are there when that address is opened again, because the address no longer changes.

R10. Only this computer can reach it. The server answers only on this computer. A request naming a host that is not one of Lahe's own names is refused, so a website cannot reach a page by pointing its own domain at this computer.

R11. Light when idle. The plan measures the always-on server in two states, and sets a limit for each before building: nothing open, and Ken's usual number of Lahe tabs left open overnight. Both are compared with today's helper plus its page servers.

R12. Agents are told. lahe review prints the stable address. The skill, the contract inside every review, docs/CLI.md, docs/ongoing/LIBRARY.md, docs/ongoing/SESSION_OWNERSHIP.md, and the diagrams describe the new addresses and the always-on server. None of them still describes per-session page servers or random ports.

R13. A worktree document survives its worktree. When a file served from a worktree is gone because the worktree was removed, its address shows the same file from the main checkout, read-only, if it exists there, with a note saying it moved. Commenting on it starts from the Library, as other moved documents do.

R14. Wrong or gone addresses say so. A name Lahe does not know shows a short page saying so, with a link to the Library. A file that is gone, with no main-checkout copy, shows a page naming the file and linking to the Library.

R15. The Library has a stable address. The Library answers at library.lahe.localhost:<port>, and at 127.0.0.1:<port>/catalog as today. No folder can take the name library.

UX Notes

  • The address bar is the UI. A name Ken can read at a glance matters more than a short one: ongoing.lahe.localhost:7817/STABLE_ADDRESSES.md beats 127.0.0.1:56055/STABLE_ADDRESSES-bd14d360685f150a.html.
  • The fallback is not an error. A .lahe.localhost address works the same way; it is only longer.
  • Typing an address by hand: .lahe.localhost addresses work typed as they are. A .lahe address typed without http:// may make the browser search instead. Links from history and bookmarks work either way.

Analytics / Logging

The helper log records, once per start: the port, whether .lahe or .lahe.localhost is in use and why, and whether the login item is installed. It records each new name given to a document, and each refused request with an unknown host name (without the page content). lahe status shows the same state. No other analytics: this is a local tool.

Rollout / Flags

No flag. The install step is the switch: until it runs, Lahe behaves as requirement 7 (starts at login) describes for a clone: the server starts on first use, and addresses stay the same while it runs. Pages opened before the change stay dead, and the Library's Open moves each to its stable address. Uninstall removes the login item and the .lahe setup; the names and the .lahe.localhost addresses keep working whenever the server runs. The login item names the Node that ran the install, the same way npm run install-cli does today. Removing that Node means running the install again, and lahe status says so.

Questions and Decisions

Resolved

Settled by Ken on the decisions page, 2026-10-11:

  • Is the always-on server acceptable? Yes. It starts at login and stays up.
  • A port per document, or one port with a name per document? One port, a name per document. Each name is its own browser origin, which also answers the worry about one page reading another.
  • .lahe or .lahe.localhost? .lahe from the start, with .lahe.localhost as the fallback. .lahe becoming a real internet ending is unlikely; deal with it then.
  • Login item, or a Mac menu-bar app? The login item ships with this feature. The menu-bar companion app, with its Library link, is a follow-up.
  • Is an install step acceptable? Yes. It is for setup only; no outside packages.
  • Core platform rule: the core is a plain server that runs on Mac, Linux, and Windows. Mac-only pieces are companions on top.
  • Deleted files: not a concern for this feature. A plain "file is gone" page is enough.

Chosen by the brief, for Ken to overrule in review:

  • Which systems get .lahe now: macOS, as an option. .lahe.localhost works everywhere.

  • Worktree documents: a gone worktree file is shown read-only from the main checkout when the same file exists there (requirement 13).

  • The name is per folder, not per file. The architecture review showed per-file names break Markdown images and links, folder sites, the rail rules, and how comments are tied to files. The folder is today's isolation unit, so nothing gets weaker. The address still reads as folder plus file.

  • Other accounts on the same computer can reach pages whenever the server runs. Recorded as a known limit; lahe install warns on a computer with more than one user.

  • How long a document keeps its name after its file is gone: forever. Names are small, and keeping them means an old bookmark still says what it was.

Open

Q1. Which ending does lahe review print: .lahe.localhost or .lahe? Ken chose .lahe. Both architecture reviews found that a plain http://name.lahe address is not "secure" to the browser, and that costs five things:

  • the address bar shows "Not secure";
  • copy buttons lose the clipboard and need an older copy method;
  • the guard against two tabs of one document both acting turns off;
  • the browser stops sending headers the Library's safety checks rely on;
  • on a machine where Lahe does not control .lahe lookups, someone on the network could take over a name.

.lahe.localhost has none of these, needs no setup on any system, and its addresses survive an uninstall.

Recommendation: print .lahe.localhost. Keep .lahe as a Mac option that answers the same names, for typing by hand. If Ken still wants .lahe printed, the plan adds the copy, tab-guard, and header fallbacks (task 6.3), and the "Not secure" label stays.

PM review: Stable addresses brief

Reviewer: PM persona, 2026-10-11. Read against Ken's directive, the crucible, the decisions page (docs/ongoing/STABLE_ADDRESSES.md), docs/ongoing/LIBRARY.md, the system overview and session ownership diagrams, and docs/BULLETIN.md.

Summary

The brief is faithful to what Ken asked for. It names the real problem (nothing answers at an old address, and the address says nothing about the page), and it carries every decision Ken settled. Twelve findings, worst first. One blocker: switching between the .lahe and .lahe.localhost endings changes every address, which brings back the dead tabs the feature exists to remove. Six are important, mostly gaps where the brief does not say what "a document" is or leaves Ken's most common case (docs in worktrees) out by accident. None of the findings disagree with what Ken asked for.

Findings

RF1. Changing the address ending kills every address made under the other one

severity   blocker
kind       defect
where      Requirements, R6 (".lahe with a fallback"); Rollout / Flags; UX Notes, second bullet
what       An address is only stable if its ending never changes, but the brief switches endings at install, at uninstall, and whenever the setup breaks.
why        Before the install, Ken's tabs and history fill with `.lahe.localhost` addresses. The install moves new addresses to `.lahe`. If those old ones stop answering, or if a broken setup flips him back, he gets the dead tabs and lost drafts the feature exists to end. Drafts are kept per address, so they do not cross endings either. The UX note "the fallback is not an error" hides this.
fix        Add a requirement: an address handed out under either ending keeps loading for as long as the server runs. The server answers both endings for every name. The only exception is a `.lahe` address while `.lahe` lookup is off, and `lahe status` says so. Say plainly whether drafts follow a document from one ending to the other, or accept that they do not and list it as a non-goal.

RF2. "Keeps working after a reboot with no command" is only true after the install

severity   important
kind       defect
where      R1 ("An old address keeps working") and R7 ("Starts at login on every system")
what       R1 promises an address works after a reboot with no command run, while R7 says a clone with no install starts the server only when `lahe review` runs.
why        The two requirements cannot both be tested as written. A tester on a clone install fails R1 on the first reboot. It also leaves open whether an uninstalled server still stops itself when quiet, as the helper does today. If it does, "stable for as long as it runs" is close to today's behavior and the clone user gains little.
fix        Scope R1 to an installed Lahe. Then say in one line what a clone user gets: does the server stay up until logout once started, or stop when quiet as today?

RF3. The brief never says what "a document" is

severity   important
kind       defect
where      Summary; R3 ("The address names the document"); R4 ("Documents stay walled off"); R8 ("Every existing document can get an address")
what       The address belongs to "a document", but Lahe has reviews, pages inside a review, linked pages, and the same file reviewed many times.
why        The Library already folds "several reviews of one document" into one row, and one review can hold several pages. If a new `lahe review` of the same brief gets `stable-addresses-2`, Ken's history fills with near-duplicates and the old address shows an old review. If each linked page is its own origin, links between pages and relative images could break. This brief itself links to the decisions page. These are product choices Ken would notice, not build details.
fix        Add one sentence defining the unit: an address names one file on disk. Add two requirements: (a) serving the same file again, in any review, gives the same address; (b) links between Lahe pages, and images and styles a page loads by relative path, keep working. If (a) is not wanted, say what Ken sees instead.

RF4. Docs in worktrees, Ken's most common case, are left out by accident

severity   important
kind       risk
where      Non-Goals, third bullet ("Not a better story for deleted or moved files"); Questions, "how long a document keeps its name"
what       Most of Ken's feature docs, this brief included, are written in a worktree that is torn down once the feature merges. The same file then lives on in the main checkout.
why        Under the brief as written, every feature doc's address turns into "this file is gone" the day its worktree is removed. That is a dead tab with a nicer message. Ken said deleted docs are not his concern; a worktree doc is not deleted, it moved. The Library already serves "the main-repo copy of a worktree" on pick-up, so the idea exists in the product.
fix        Add an open question for Ken: when a worktree is gone, should its addresses serve the main-checkout copy of the same file? If he says no, name worktree teardown in the non-goal, so the gap is chosen rather than missed.

RF5. "Light when idle" measures the wrong idle

severity   important
kind       risk
where      R11 ("Light when idle")
what       R11 measures the server with nothing open, but Ken's normal state is many Lahe tabs open across days.
why        Today most of those tabs are dead, so they cost nothing. Once every address answers, every open tab is live and polls the helper. The bulletin row LAHE-idle-battery-cost (battery drain with review tabs open, with a visible tab polling once a second) shows this is where the cost is. "No CPU" is also an absolute no test can pass, since the helper already runs 15-second checks.
fix        Measure two cases: nothing open, and a realistic count of open tabs (taken from Ken's own browser) left overnight. Replace "no CPU" with a number the plan sets and then measures.

RF6. Which systems get the .lahe setup in this feature is unclear

severity   important
kind       risk
where      R6 (".lahe with a fallback"); R7 ("Starts at login on every system"); decisions page, "Your rule for this"
what       The decisions page calls the `.lahe` ending "an optional extra per system". The brief reads as if the one-time `.lahe` setup ships for macOS, Linux and Windows at once.
why        Each system sets up name lookup differently. The plan cannot size the work, and a tester cannot tell whether Linux or Windows on `.lahe.localhost` passes or fails.
fix        State it: the login item ships on all three systems. The `.lahe` setup ships on the systems Ken names now (likely macOS), and the others use `.lahe.localhost` until it is added. Put each system that is left out under Non-Goals.

RF7. "Not a change to agent sessions" is not true, and agents will act on it

severity   important
kind       defect
where      Non-Goals, sixth bullet ("Not a change to agent sessions, takeover, or the monitor"); R12 ("Agents are told")
what       Sessions stop owning page servers. Closing a session no longer stops anything. Takeover no longer reopens servers. The helper's stop-when-quiet rule and the reopened-session sweep lose their reason to exist.
why        A reader, or an architect agent, will take "not a change" at its word and leave those rules in place or skip their docs. R12's list of docs to update leaves out `docs/ongoing/LIBRARY.md` (its "Helper lifetime" section) and `docs/ongoing/SESSION_OWNERSHIP.md`, which describe exactly these rules.
fix        Reword the non-goal: "Sessions keep owning reviews, takeover and the monitor. What changes is that a session no longer starts or stops page servers." Add the two missing docs to R12's list.

RF8. Three requirements are hidden in other sections

severity   minor
kind       defect
where      UX Notes, fourth bullet (the Library at `library.lahe`); Non-Goals, first and third bullets
what       The Library's own stable address, the "this file is gone" page, and "the Library's Open moves an old tab to its stable address" are all promises, but none is a numbered requirement.
why        Promises outside Requirements do not reach the plan's test list. The Library bookmark is the one Ken uses to get back to everything else, so it matters most. A document whose name comes out as `library` would also clash with it.

RF9. Most names will come from file names, not titles

severity   minor

RF10. The related bulletin rows are not named

RF11. A port clash and a mistyped name do not say what Ken sees

severity   minor
kind       defect
where      R5 ("One port for every document"); R10 ("Only this computer can reach it")
what       R5 reports a port clash only in the log and `lahe status`, and says the port is "picked once at install", with no word on clone use. R10 refuses an unknown host, but does not say what a mistyped `something.lahe` name shows.
why        When the port is taken, every document is dead and the browser says only "can't connect". Ken will not think to run `lahe status`. A typo under Lahe's own ending is a Lahe name, not a foreign site, and a bare refusal looks like a dead tab.
fix        Have `lahe review` also print the clash and what to do about it. Say that the port is never changed on its own, since a change kills every address. Say that an unknown name under a Lahe ending shows a short "no document by that name" page with a link to the Library.
