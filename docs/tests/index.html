What the suite is for

The tool this project replaces had no browser-level test at all, and every symptom it produced lived in the part that had none. So the suite is built around a rule: if an assertion needs layout, a caret rectangle, a real key event, or a real Content-Security-Policy header, it runs in a real browser or it does not count. jsdom is banned repo-wide and the lint check enforces it.

There are two lanes:

  • Unit (test/unit, Node's built-in node:test): the logic that does not need a page. Wire formats, path safety, projection, command dispatch, the anchor engine against a simulated DOM.
  • Browser (test/browser, Playwright): the real thing. A real lahe review walk, a real helper process, a real static server, a real injected script line, and a real page a reviewer touches.

One more rule the suite enforces on itself: no arbitrary sleeps. Every wait is a condition poll or a counter read, and a unit test scans every file under test/ and fails the gate on a sleep. A flaky browser test gets its determinism fixed, never its assertion loosened.

The three gates

Three gate commands exist and they are not interchangeable.

npm run gate:alllint (node --check over every tracked .js file, plus no jsdom, plus manifest completeness); check:layer (fails when the committed bundle dist/lahe-layer.js is stale); test:unit (node --test over test/unit); test:browser:all (Playwright, Chromium and Firefox and WebKit)The orchestrator, at a checkpoint. The three-browser run.

To run one browser lane by name, the environment flag has to come along, because the Playwright config reads process.argv to decide which projects exist and the worker process does not carry the flag:

LAHE_ALL_BROWSERS=1 npx playwright test --project=webkit

Single lanes otherwise: npm run test:unit and npm run test:browser. Browsers install once with npx playwright install chromium, plus npx playwright install firefox webkit for the other two lanes.

How to read a test's name

Test names here are claims, not labels. A label says what area the test touches. A claim says what has to be true, in the order it happens, in words a person can check against the running tool. So the titles read as sentences:

  • "a reload waits while the reviewer is still touching the page, then lands"
  • "the comment survives the rebuild and the card still points at the right paragraph"

The pattern is: the thing that happens, then the thing that must still be true afterward. When you read a failure, the title is the sentence that stopped being true. That is the whole reason for writing them this way.

Two sets of names are cross-references rather than prose, and they mean something specific:

  • S1 through S8 are the graceful-failure net: the eight ways the element stamp can be confidently wrong. Each one is a rebuilt page that lies to the engine in a different way, and each has to end the same way. Nothing written, the record marked lost with a sentence the reviewer can read, and the page left exactly as the rebuild left it. They are defined in docs/ongoing/FINGERPRINTING.md and carried by name into graceful_failure.spec.js and anchor_cases.test.js.
  • Numbered fingerprinting cases (case 1, case 4b, case 6b, and so on) are the use cases in the same document: finding the right element to edit, showing where an edit was made, surviving a rebuild. A test titled "case 4b" is answering that numbered case, and the document is where the case is described.

If a title reads as a claim you cannot check, that is a bug in the title. Fix the title.
